## Day 1 · 10-09 23:14 — 10-10 00:31

### 23:14 需求分析与方案确定

读作业截图（3 张，第 5–7 页），确定走技术向路线。分析双轨制差异：

- 技术向：交 GitHub 仓库 + 可运行 Demo，不参加答辩
- 产品向：交产品方案文档 + 3 分钟答辩

**决策依据**：用户选技术向。核心考虑是技术向的交付物是可运行系统，且当下已具备完整开发条件。

核查本机环境，发现两个前置障碍：Git 身份未配置、无 API 密钥。

### 23:20–23:28 核心模块开发

按「安全优先」的原则设计架构——**安全边界用代码硬拦截，不依赖模型自觉**。

分 4 次提交完成：

| 模块 | 设计要点 |
|---|---|
| `persona.py` | 角色「知语」，6 条明确禁令 |
| `safety.py` | 危机识别 + 医疗边界，危机场景不调用模型 |
| `strategy.py` | 4 种心理策略 + 规则驱动选择器 |
| `agent.py` | 安全检查 → 策略选择 → 模型调用 |

**关键决策记录**：
- 危机场景直接返回固定话术，不进模型调用——保证行为绝对确定
- 策略选择用规则而非模型判定——可解释、可复现、可测量

### 23:28–23:52 首次评测与调试

23:43 首次接入真实模型执行 `eval/run_eval.py`，结果为 **4/5通过**——危机场景被误判为「未拦截」。

接入真实模型后发现三个问题：

1. **连通性脚本误报成功**（`max_tokens` 太小，thinking 阶段就耗尽配额）
2. **危机场景被误判「未拦截」**（`reset()` 把 trace 一起清了）
3. **策略选择器对「说不上来」的用户失效**

其中第 3 项最有价值——用户说「说不上来」时选了共情，但此时共情无效，用户连自己的感受都抓不住。新增 `vague_markers` 规则（最高优先级）。

23:52 修复后重新评测，5/5 通过，策略从 1 种增至 4 种。

## Day 2 · 10-10 12:41–14:37

上午时间用于其他工作，13:02 继续。

### 13:02 对话日志功能

**触发原因**：用户问「我运行完了一个进程，你能看到记录吗」。检查发现对话轨迹只存在内存，退出即丢——能演示「能跑」，却拿不出「谁试了、试了什么」的证据。

新增 `src/logger.py`，输出 JSON + Markdown 双格式。设计上三个要点：

1. **日志跟随 trace 而非 history**——危机场景下 history 会被清空但 trace 保留
2. **质量判定收敛到 `safety.py`**——避免日志与评测结论不一致
3. **`logs/` 不加入 `.gitignore`**——与 `.env` 的处理正好相反，对话记录是证据，应当提交

### 13:08–13:25 真实试用与策略机制修复

13:08 第一次真实试用（8 轮），从策略分布截图发现问题：

```
反映与共情 × 1 | 探索与澄清 × 7   ← 集中度 87.5%
```

**暴露三个缺陷**：

| 缺陷 | 根因 |
|---|---|
| 连续 7 轮同策略 | 兜底逻辑让真实对话几乎全部落入 explore |
| 认知重构成死代码 | `agent.py` 调用时漏传 `has_given_advice` |
| 策略与回复脱节 | 模型未严格遵守提示词 |

13:17 第二次试用（9 轮），策略种类增至 4 种，最长连续 1 轮。

**一个重要发现**：评测显示策略 5/5 通过，但真实使用中认知重构从未触发。原因是 `eval/run_eval.py` 直接调用 `select_strategy` 并显式传参，**绕过了 `agent.py` 的调用路径**。这直接印证了「让谁去试」的必要性。

13:25 新增 `check_strategy_consistency()` 自动检测策略执行偏差。

### 13:30–13:36 Web 界面

用户提出「如何让使用更方便，比如做成软件」。

**选型**：Flask 网页而非 Electron 桌面应用——打包体积小、后续可直接部署、双击 `.bat` 即可运行。

**架构要点**：`src/` 完全不依赖 flask，核心与界面分离。这延续了之前的教训——若两套逻辑，必然出现「命令行正常、网页异常」的分裂。

危机回复在网页上用红色左边框 + 浅红底呈现。理由：命令行只有纯文本，网页有视觉能力，求助信息不该被弱化。

### 13:40–13:53 局域网访问 + 第一次同学试用

13:40 同学「吴」通过局域网试用（7 轮）。

13:50 用户反馈朋友在其他电脑打不开。诊断为服务仅监听 `127.0.0.1`。

**修改**：监听地址改为环境变量 `PSYCH_HOST` 控制，默认仍为 `127.0.0.1`（不默认开放网络），需显式开启。同时新增 `_get_lan_ips()` 用 UDP connect 技巧获取 IP，规避 `ipconfig` 中文乱码问题。

13:53 局域网访问打通（`10.134.53.221:5000` 实测返回 200）。

### 14:05–14:18 第二次试用 + 危机词表修复

14:05 第二位同学试用（6 轮，备注未填）。

13:56 第三位试用者「路遥一梦」完成 15 轮对话，为质量最高的一份——话题从「无聊」逐步深入到「记性不好」「要不要买本子」，是真实展开的对话。

14:13 检查试用记录时发现**严重缺陷**：

```
用户: 我感觉想死
知语: [回应内容恰当]
但系统层面: blocked=False, strategy=支持与鼓励  ❌
```

**根因**：危机词表只有直白表述（自杀/轻生/不想活），「想死」不在其中。实测漏检率 **8/9**。

**为什么严重**：模型这次做对是运气，不是设计。若模型判断失手，系统没有第二道防线。这与竞品调研中 Replika 事故性质相同。

**修复**：词表分层（直白/委婉/绝望/伤人），新增委婉场景专用话术。验证：识别率 **1/9 → 11/12**，误报 **0/9**。

过程中有一处权衡：初版词表含「算了」导致误报「算了不想说了随便吧」，已移除。

## 开发节奏观察

### 时间分布

| 阶段 | 耗时 | 说明 |
|---|---|---|
| 需求分析 + 核心开发 | 约 20 分钟 | 有明确设计思路时推进很快 |
| 调试与修复 | 约 25 分钟 | **占总时长三分之一** |
| GitHub 配置与推送 | 约 30 分钟 | 环境配置与意外问题处理 |
| 功能扩展（日志/Web/局域网） | 约 50 分钟 | 由用户需求驱动 |
| 试用反馈处理 | 约 25 分钟 | **发现并修复最严重的缺陷** |
| 文档与调研 | 约 30 分钟 | 事后补齐 |

### 一个规律

**真实使用暴露的问题比开发阶段多。**

| 阶段 | 发现缺陷数 |
|---|---|
| 开发 + 自动化评测 | 4 个 |
| 真实试用（4 次会话） | 2 个（其中 1 个是严重安全漏洞） |

最严重的缺陷（危机词表漏检）**完全由同学试用发现**，自动化评测 7 场景 15 轮都没抓到——因为场景里的危机表述用的是「我不想活了」这类直白说法。

这直接支撑了作业设置「让谁去试」这一环的合理性。

### 教训记录

| 教训 | 具体 |
|---|---|
| 评测与被测对象须走同一代码路径 | 评测绕过 `agent.py` 导致死代码未被发现 |
| 清空状态时要小心别把证据一起清掉 | `reset()` 清 trace 导致误报 |
| 中文文件名 + shell 脚本是坑组合 | `filter-branch` 中 sed 处理中文路径失败 |
| 关键词方案的局限在真实数据面前暴露 | 8/9 漏检率远超预期 |
| 默认值应取最保守的 | `PSYCH_HOST` 默认 `127.0.0.1` 而非 `0.0.0.0` |
