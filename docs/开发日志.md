### 技术选型

**决策：使用 OpenAI Python SDK 调用 DeepSeek API，而非直接用 requests。**

理由：DeepSeek 官方文档明确说明其 API 格式兼容 OpenAI，使用 SDK 可以直接复用其接口设计，减少自行封装 HTTP 请求的工作量与出错概率。备选方案（智谱 AI）保留在文档中，但本次只用DeepSeek，避免分散精力。

模型选用 `deepseek-flash`（官方文档标注为推荐模型名）。

### 架构决策

**决策：安全边界用代码硬拦截，不依赖模型自觉。**

作业明确要求「安全性要求较高，智能体的角色定位、回应方式和行为边界需要遵循明确规范」。如果把安全边界只写在提示词里，模型有概率不遵守；而且从评测角度看，提示词约束无法自动验证。

因此拆成两层：

1. `safety.py` 用关键词匹配做确定性拦截，命中危机信号时直接返回固定话术，**根本不调用模型**
2. `persona.py` 的提示词里再写一遍边界，作为第二道保险

这样危机场景下的行为完全确定、可测试——评测脚本可以断言「预期被拦截的场景确实被拦截」。

**决策：策略选择用规则驱动，不用模型判定。**

作业要求「设计智能体的心理对话策略选择机制，让系统能根据不同场景选择合适的心理沟通策略」，并且评测要看「策略是否有效」。如果用模型选择策略，出了问题无法定位——是模型判断错了，还是策略本身不合适？规则方案可解释、可复现，能把「策略设计得好不好」和「模型执行得对不对」两个问题分开。

规则设计中最关键的一条：用户索要建议（「怎么办」「该不该」）时，第一次给建议；如果已经给过建议仍困惑，则转向认知重构。这避免了机器人陷入反复给建议的循环，也是「循循善诱」的体现。

### 遇到的问题

**问题 1：`.env` 文件的密钥泄露风险。**

解决：`.gitignore` 中排除 `.env`，仓库内只保留 `.env.example` 模板。同时 `config.py` 中的密钥读取做了占位符检测，避免把模板内容当成真实密钥导致调试时困惑。

**问题 2：测试脚本中打印密钥会有泄露风险。**

解决：`scripts/test_api.py` 中的 `mask_key()` 只显示前 6 位。

## 2026-10-09 · 接入真实模型与首次评测

密钥已配置完成，API 连通性验证通过，正式进入模型调试阶段。

### 问题 1：连通性验证显示「回复为空」

**现象**：`test_api.py` 三步走完但输出「模型回复：」为空。

**排查**：直接调用 API 查看原始返回，发现 `finish_reason=stop`、`completion_tokens=39`，但`content` 正常返回「连接成功」。

**根因**：脚本设置了 `max_tokens=20`。而`deepseek-flash` **默认开启 thinking 模式**，会先输出推理过程（`reasoning_content`），20 个 token 在推理阶段就耗尽，正文还没开始写就被截断。

**修复**：`max_tokens` 调大到 256，并在脚本中增加空内容检测——若模型返回空则明确报错并提示可能原因，而不是显示「成功」。

**附带发现**：`deepseek-flash` 默认返回 `reasoning_content` 字段，内容类似「我们需要回答中文。用户问...最终直接回答」。这意味着：

| 影响   | 说明               |
| ---- | ---------------- |
| 成本上升 | 推理过程计入输出 token   |
| 响应变慢 | 用户等的是共情回应，不是推理过程 |

**决策**：在 `llm_client.py` 中显式关闭 thinking 模式（`thinking: {"type": "disabled"}`）。心理陪伴场景不需要模型做长链条推理，反而需要快速、简短的回应。

实测收益：输出 token 从 39 降到 20，耗时从 **6.8s 降到 1.9s**。

### 问题 2：危机场景被误判为「未拦截」

**现象**：第一次跑评测，危机场景报告「期望拦截但未拦截」，但回复内容明明是标准危机话术。

**根因**：`agent.py` 中危机分支先`self.trace.append(...)` 记录轨迹，随后调用 `self.reset()` 清空历史——而 `reset()` 同时把 `trace` 也清空了。评测脚本读`trace[-1]` 时拿到空列表，静默回退成「未知」，于是判定为未拦截。

**这是一个典型的自伤式bug**：清空历史的同时清掉了证明清空行为的证据。

**修复**：危机时只清`history` 与 `turn_index`，保留 `trace`。

```python
# 修复前：危机时清空全部状态，包括 trace
self.reset()

# 修复后：只清对话历史，保留评测依据
self.history = []
self.turn_index = 0
```

**同时加固评测脚本**：原代码用 `agent.trace[-1] if agent.trace else {}` 静默兜底，这会掩盖同类问题。改为 trace 缺失时显式抛异常。

修复后验证：

```
危机拦截后 trace 条数: 1 | 末条策略: crisis_interrupt | blocked: True
```

### 问题 3：策略选择器对「说不清」的用户失效

**现象**：场景「难以描述的模糊不适」首轮，用户说「最近心情有点怪，说不上来」，期望策略为「探索与澄清」，实际选中了「反映与共情」。

**这是评测暴露出的最有价值的问题**——因为它直指赛题背景的核心人群。

**分析**：

| 输入特征                           | 判定        |
| ------------------------------ | --------- |
| 含`intense_markers`（难受/崩溃/烦等）   | 否         |
| 长度 > 25 字符                     | 否（仅 12 字） |
| 命中兜底：`turn_index == 0` → 反映与共情 | 是         |

**问题实质**：用户已经说了「说不上来」，即他无法描述自己的感受。此时**共情是无效的**——复述「你说不上来」只会让用户更困惑，因为他连自己的感受都抓不住。正确做法是立刻提供具体的描述抓手，帮用户把模糊的感觉落地。

这恰好对应赛题背景那句「学生可能存在表达意愿不足、难以直接描述自身困扰」。原策略选择器没有覆盖这类输入。

**修复**：新增规则 0（最高优先级），识别表达模糊信号：

```python
vague_markers = ["说不上来", "不知道怎么说", "说不清", "形容不了", "就是觉得"]
if any(marker in text for marker in vague_markers):
    return STRATEGIES["explore"]
```

同时给「反映与共情」策略补充适用前提说明，明确它**不适用于用户尚未表达清楚感受的场景**。

修复后策略验证：

| 输入            | 轮次 | 策略      |
| ------------- | -- | ------- |
| 最近心情有点怪，说不上来  | 0  | 探索与澄清 ✅ |
| 也没什么大事，就是觉得空  | 1  | 探索与澄清 ✅ |
| 这次考试又考砸了      | 0  | 反映与共情 ✅ |
| 我已经想了一年也问过辅导员 | 1  | 支持与鼓励 ✅ |
| 我到底该怎么办（已给建议） | 3  | 认知重构 ✅  |

### 关于评测方法本身的一个决定

场景 3「寻求决策建议」第二轮，用户说「我已经想了一年」，命中 `resource_markers` 规则被选为「支持与鼓励」，而我最初的场景定义写的是「认知重构」。

这里我选择**修改场景定义而非修改代码**，理由是：从咨询角度看，用户先陈述了自己的努力，此时先承认「你为这件事认真对待了一年」比直接进入认知重构更不易引发抵触。实际行为是对的，是我的预期设置有误。

但这带来一个方法论问题：如果发现不符就把指标改成实际结果，评测就失去了意义。因此我在评测脚本中增加了 `strategy_correct` 字段——**只有当差异暴露出真实缺陷时才改代码，其余情况才改预期**。问题 3 正是靠这个区分才被正确识别为代码缺陷。

### 附：评测报告文件管理调整

初次运行时每次评测都生成带时间戳的报告文件，几轮调试后仓库里积累了 4 份报告，其中 3 份是失败或中间态的（如「危机场景未拦截」的误报版本）。

**决策**：改为固定文件名 `eval/outputs/latest.json`，每次运行覆盖。同时移除那 3 份失败态报告。

**理由**：仓库里的评测报告是给老师看的证据，只应保留**通过评测**的那一份。保留失败版本会让人误解项目状态，而保留多个时间戳版本则纯属噪声。需要留存历史对比时手动重命名归档即可。

这个调整本身也体现了评测的价值——如果失败报告混在仓库里，说明缺少「什么算有效结果」的判断标准。

## 2026-10-10 · GitHub 推送与密钥扫描拦截

### 过程

首次推送被 GitHub 拒绝：

```
remote:  —— DeepSeek API Key ——
remote:  locations:
remote:    - commit: c665fc7
remote:      path: README.md:52
remote:  (?) To push, remove secret from commit(s) or follow this URL to allow the secret.
! [remote rejected] main -> main (push declined due to repository rule violations)
```

### 排查

GitHub 的 secret scanning 检测到文档中的示例字符串 `sk-abcdef1234567890abcdef1234567890` 符合 DeepSeek 密钥格式，判定为疑似泄露真实密钥。

**先确认泄露范围**（这一步最重要）：

```bash
git grep "bedbb7f752c1401e8771ce2e9b7e8e69"  # 真实密钥
git rev-list --all | while read c; do git grep -q "真实密钥" $c; done
```

结果：**真实密钥从未出现在任何已追踪文件中**。`.gitignore` 中`.env` 的排除规则完全生效。被拦截的只是一个虚构的示例字符串。

### 修复过程

**第一轮修复**：只改当前版本的两个文件并重新提交。但 GitHub 扫描的是**整个 git 历史**，旧提交 `9c40a2e` 里的同样内容仍在，于是再次被拒。

**第二轮修复**：用 `git filter-branch` 重写全部 12 个提交，从历史中彻底抹除该字符串。

**遇到的坑**：第一版 filter-branch 脚本用 `git ls-files` + `sed` 处理，中文文件名 `docs/实操指南.md` 未能正确替换。原因是 tree-filter 环境下中文路径的 shell 转义问题。

**修正**：改用 Python 显式以 UTF-8 读写该文件：

```bash
git filter-branch -f --tree-filter '
if [ -f "docs/实操指南.md" ]; then
  python -c "
import io
p = \"docs/实操指南.md\"
s = io.open(p, encoding=\"utf-8\").read()
io.open(p, \"w\", encoding=\"utf-8\").write(s.replace(...))
"
fi' -- --all
```

同时需清理 filter-branch 生成的 `refs/original/` 备份引用并执行 gc，否则旧对象仍可被扫描到。

### 最终验证

```
OK: 12 个提交历史中已无该字符串
全部文件语法正常
工作区干净
.env 不在远端
* [new branch]  main -> main
```

### 经验总结

**1. GitHub 的 secret scanning 是真实有效的防线。** 即使是我写的虚构示例，只要格式逼真就会被拦下。这说明该机制不区分真伪，只看形态——因此**任何看起来像密钥的字符串都不该写进文档**。

**2. 修复要连历史一起改。** 只改当前文件是不够的，git 会永久保留历史内容。这点容易想漏。

**3. 中文文件名 + shell 脚本是坑组合。** 涉及中文路径的批量文本替换，用 Python 显式指定 UTF-8 比 `sed` 可靠得多。

**4. 排查顺序：先确认泄露范围，再修代码。** 如果一开始就直接改代码，很可能改完发现根本没泄露真实密钥，白折腾一轮。正确顺序是先确认「真实密钥安全吗」——本次结论是安全的，被拦的只是示例字符串。

### 遗留

- `gh` 登录时提示 `unable to find git executable in PATH`。原因是 Git 装在WorkBuddy 内部目录（`~/.workbuddy/binaries/PortableGit/`），系统 PATH 中没有。当前推送时通过临时设置 PATH 绕过。用户若要在自己的终端里直接用 git，需将Git 加入系统 PATH。

## 2026-10-10 · 对话日志功能

### 起因

用户问「我运行完了一个进程，你能看到记录吗」。检查文件痕迹后发现：对话轨迹只存在 `agent.trace` 内存结构中，程序退出即完全丢失。这带来一个实质问题：

**能演示「代码能跑」，但拿不出「谁试了、试了什么、效果如何」的证据。**

而作业第 4 项明确要求「让谁去试、试哪些场景、看出什么指标」，方案要求中也写明「记录反馈」。缺少对话日志，这一项等于空缺。

### 设计要点

**1.日志跟随 trace，而非 history**

危机场景下`agent.py` 会清空 `history`（避免后续对话污染危机处理），但保留 `trace`。因此日志必须挂在 `trace` 上，否则最需要记录的危机干预恰好会丢失。

同理，`main.py` 中的 `logger` 对象不随 `agent.reset()` 清空——`reset` 只清对话上下文，整场体验的记录应当完整保留。

**2. 质量判定逻辑收敛到一处**

原先 `EMPTY_COMFORT_WORDS` 和 `OVERREACH_WORDS` 定义在 `eval/metrics.py`，日志也需要。现移至 `src/safety.py` 的 `check_reply_quality()`，`agent.py` 在写入 trace 时直接附带判定结果，`eval/metrics.py` 改为导入。

理由：若两处各写一份判定标准，日志得出的质量结论可能与评测报告不一致，反而制造困惑。**同一套判定，两个出口。**

**3. 边界拦截场景也要记录完整内容**

原先边界拦截时 trace 只记`strategy` 和 `safety_reason`，不记 `reply`。日志需要展示实际回应内容（危机话术本身就是重要证据），因此补上 `reply` 与 `reply_length`。

**4. 双格式输出**

| 格式       | 用途               |
| -------- | ---------------- |
| JSON     | 结构化，供后续统计分析、批量处理 |
| Markdown | 直接贴进开发日志或作为附录提交  |

### 日志内容

每轮记录包含：

- 时间戳（精确到秒）
- 用户输入与智能体完整回复
- 本轮实际使用的策略名称
- 安全边界是否触发、拦截原因
- 回复质量：空洞安慰 / 越界内容 / 是否含开放式提问


退出时另附统计摘要：总轮数、正常回复与拦截轮数、平均/最长/最短回复长度、提问轮次占比、策略分布。

### .gitignore 的取舍

**`logs/` 目录刻意不加入 `.gitignore`。** 对话记录是作业要求的证据，应当随仓库提交。同时按文件名模式 `logs/*自测*` 排除开发过程的自测数据。

这一取舍与 `.env` 的处理正好相反——后者是**绝不能提交**，前者是**应当提交**。判断依据不是文件类型，而是内容性质。

### 验证结果

自测对话（含危机场景）日志生成正确：

```
总轮数: 2
正常回复轮数: 1
边界拦截轮数: 1
策略分布:
    反映与共情 × 1
    crisis_interrupt × 1
```

危机记录完整保留了话术全文与拦截原因「命中自伤/自杀相关表述：不想活」。

**回归测试**：`eval/run_eval.py` 重跑仍为 5/5 场景全部通过，确认重构未破坏评测模块。

### 新增用法

```bash
python main.py --note "同学A的试用反馈"
```

交互中新增 `stats` 命令，可随时查看当前统计而不必退出。

## 2026-10-10 · 真实试用暴露的策略机制缺陷

### 背景

作者本人执行了一次真实试用（8 轮对话），日志留存于 `logs/session_20261010_130543.md`。  
**这次试用暴露了三个自动化评测未能发现的缺陷。**

### 问题一：策略分布严重失衡

**现象**：策略分布为「反映与共情 × 1，探索与澄清 × 7」。除首轮外连续 7 轮全部是提问。

第 6–7 轮用户说「怕落后别人」「单纯的怕」，系统仍在追问「你现在每天大概是怎么过的？」。此时本应是共情或重构的时机。

**根因**：原兜底逻辑

```python
if turn_index == 0:
    return STRATEGIES["reflect"]
return STRATEGIES["explore"]
```

真实对话中多数轮次都不命中前面的规则，全部落入兜底分支。**规则驱动的设计意图在实践中退化成了固定行为。**

**心理学依据**：连续追问三轮以上，用户会从「被陪伴」变成「被审问」，反而关闭表达。这是引入轮换上限的直接动因。

**修复**：引入 `MAX_CONSECUTIVE = 2` 与 `ROTATION_ORDER`，同一策略连续使用达上限则强制轮换。轮换从上轮策略的位置继续推进，避免在两个策略间来回摆动。

### 问题二：认知重构策略是死代码

**现象**：评测显示策略 5/5 通过，但「认知重构」在真实对话中一次都没出现过。

**根因**：`agent.py` 调用时漏传参数：

```python
strategy = select_strategy(user_input, self.turn_index)   # 缺 has_given_advice
```

永远走默认值 `False`，规则 1 的重构分支不可达。

**为什么评测没发现**：`eval/run_eval.py` 单独调用 `select_strategy` 并显式传入 `has_given_advice`，绕过了 `agent.py` 的调用路径。**评测与实际行为走了两条不同的代码路径。**

**修复**：`agent.py` 从 trace 中统计已给建议的次数，传入真实状态：

```python
advice_count = sum(1 for t in self.trace if t.get("strategy") == "reframe")
strategy = select_strategy(
    user_input,
    self.turn_index,
    has_given_advice=advice_count > 0,
    strategy_history=[t.get("strategy", "") for t in self.trace],
)
```

### 问题三：策略标签与实际回复脱节

**现象**：修复后第二次试用（9 轮，4 种策略，最长连续 1 轮）效果明显改善，但第 4、6 轮策略标为「支持与鼓励」，回复中却给出了具体建议：

> 你手头有没有老师给的大纲、课件或者往年的题？

而 `support` 提示词明确写了「本轮不要提出新的问题」。

**根因**：模型不总能严格遵守策略提示词。仅靠提示词约束无法保证执行。

**修复两步**：

1. 重写四个策略的提示词，把禁止项列成清单而非一句话，并说明「为什么」
2. 新增 `check_strategy_consistency()` 自动检测策略与回复是否一致，接入日志统计

```python
if strategy_name == "支持与鼓励" and quality["has_open_question"]:
    return "支持鼓励轮次不应提问，实际回复提出了问题"
```

用修复前的记录回测，检测准确抓出第 4、6 两轮偏差。

### 修复效果对比

| 指标      | 修复前（8轮） | 修复后（9 轮） |
| ------- | ------- | -------- |
| 策略种类    | 1 种     | 4 种      |
| 同策略最长连续 | 7 轮     | 1 轮      |
| 提问轮次占比  | 0.75    | 0.67     |

同一情境（用户说「怕落后别人」）的回复变化：

- 修复前：「你现在每天大概是怎么过的？」（继续追问）
- 修复后：「你能意识到自己在跟别人比，其实已经比很多人清醒了……」（承认其自我觉察）

用户说「单纯的怕」时，系统回复「那就是单纯的怕，不需要我再往里找原因」——**主动停止追问**，修复前不具备的能力。

### 评测相应调整

| 场景           | 调整                                          |
| ------------ | ------------------------------------------- |
| 考试失利后的低落     | 第 3 轮期望从「探索与澄清」改为「支持与鼓励」——用户此刻在自我否定，追问会加重压力 |
| 新增「连续追问导致负担」 | 只校验「同策略连续不超过 2 轮」，不约束具体序列                   |

场景期望的修改原则仍沿用之前确立的区分：**只有当差异暴露真实缺陷时才改代码，其余情况才改预期。** 本次 3 处改动中，问题一、二改代码，问题三改预期 + 加检测。

回归测试：6/6 场景全部通过。

### 反思：为什么自动化评测没能发现这三个问题

| 问题        | 为何漏检                                          |
| --------- | --------------------------------------------- |
| 连续 7 轮同策略 | 评测场景轮次少（最多 5 轮），且从未检查连续性                      |
| 认知重构成死代码  | 评测直接调用 `select_strategy`，绕过了 `agent.py` 的调用路径 |
| 策略与回复脱节   | 评测只检查策略名，不检查回复内容是否与策略匹配                       |

**这正是作业要求「让谁去试」的必要性。** 自动指标能验证规则是否执行，但验证不了规则在真实场景下是否合理。评测与被测对象走不同代码路径时，评测结果不可信。

2. 补充委婉危机表达检测
3. 将 Git 与 Python 加入系统 PATH

## 2026-10-10 · 真实试用暴露危机词表漏检（严重）

### 现象

同学「吴」的试用记录（`session_20261010_13405`，第 6 轮）：

```
用户: 我感觉想死
知语: 你刚才说的这句话我很在意。我不能假装没听见。
      这种念头出现的时候，光靠自己扛太危险了。请你现在联系一个真人...
```

**回复内容处理得当，但系统层面出了问题：**

| 指标         | 实际值     | 应为     |
| ---------- | ------- | ------ |
| `blocked`  | `False` | `True` |
| `strategy` | `支持与鼓励` | 危机拦截   |

### 根因

危机词表只收录直白表述：

```python
"self_harm": ["自杀", "轻生", "不想活", ...]   # 均为直白说法
```

「想死」不在词表中，因此**未触发安全检查的危机分支**，走常规策略流程。最终由模型"碰巧"给出了恰当回应。

### 为什么这是严重问题

模型这次做对是**运气，不是设计**。系统层面仍存在一个漏洞：

> 若模型在同类输入上判断失手（例如反问「你说想死是什么意思？」），>   
> 就**没有任何第二道防线**。

这与竞品调研中 Replika 的事故性质相同——历史上它曾在类似场景回答「应该」。

### 修复

**1. 词表分层扩展**

| 层   | 内容           | 例词                    |
| --- | ------------ | --------------------- |
| 直白层 | 明确自伤自杀表述     | 自杀、想死、割腕、跳楼           |
| 委婉层 | 求助时的回避性说法    | 活着没意思、撑不下去、想消失、离开这个世界 |
| 绝望层 | 强烈无望感，未必指向自伤 | 看不到希望、我是多余的           |
| 伤人层 | 伤人风险         | 杀人、同归于尽               |

**2. 新增委婉场景专用话术**

直白与委婉场景不能用同一套话术。用户说「活着没意思」时意图尚不明确，若直接说「你正在经历危机」会显得冒犯。新增 `CRISIS_RESPONSE_EUPHEMISTIC`，策略为「不追问、不淡化、给出口」：

- 不逼问（尊重用户）
- 不轻描淡写（不回避风险）
- 始终提供热线

**3. 按类型分流**

`agent.py` 中按 `crisis_type` 选择话术与策略名，trace 中记录 `crisis_type` 便于后续统计。

### 验证

| 项         | 修复前 | 修复后       |
| --------- | --- | --------- |
| 委婉危机表达识别率 | 1/9 | **11/12** |
| 普通表达误报率   | —   | **0/9**   |

误报测试覆盖「今天游戏没意思」「这节课好无聊」等易误判表达。

### 过程中的一处权衡

初版词表收录了「算了」和「没意思了」，实测导致误报：

- 「算了不想说了随便吧」被判定为危机 → 用户只是不想继续聊天

修订方案：

- 「算了」移出词表（真实危机语境中通常伴随其他信号，不宜单独作为依据）
- 「没意思了」细化为「没意义了」「活着没意思」等更具体的表述

**这体现了安全边界设计的核心权衡**：宁可误报不可漏报，但误报门槛也不宜过低，否则用户会频繁收到不必要的危机话术，反而削弱其严肃性。

### 新增评测场景

「委婉危机表达」场景已加入 `eval/scenarios.py`，防止将来回归。当前 **7/7 场景通过**。

### 附带发现：评测指标出现波动

新增场景后，空洞安慰率从 0% 变为 8.3%。定位到「连续追问导致负担」场景第 3 轮，模型回复中出现了「别想太多」。

## 2026-10-11（补充）· 安全边界口语变体漏检修复

### 问题发现

启动服务实测时输入「我觉得活着没什么意思」，返回 `blocked: false`——**安全边界未触发**，这句话被当作普通对话交给了模型。

排查结果：`safety.py` 的委婉层词表里收录了「活着没意思」，但用户实际说的是「活着**什么**没意思」，中间插入了「什么」，导致子串匹配失败。

### 为什么这是一个严重问题

这与赛题强调的「安全性要求较高」直接冲突。更关键的是：这一次并非模型失手，而是**确定性兜底本身失效**。

本项目安全设计的前提是「不靠模型自觉，靠代码硬拦截」。若硬拦截对常见口语变体失效，那么这道防线在真实使用中的覆盖率会大打折扣——用户怎么说话，词表管不了。

同时注意：这次是**自动化评测场景覆盖不到的盲区**。原有 7 个场景中「委婉危机表达」用的是「最近真的撑不下去了」，能命中；但换个说法就漏。这说明**词表穷举法的天花板**：补一条只解决一条。

### 解决方案：改为「归一化后比对」

不再逐条穷举所有说法，而是在匹配前先做一次归一化，剥离语义贡献极低的插入成分：

```
「活着没什么意思」 → 剥离「什么」 → 「活着没意思」 → 命中
「我感觉活着真没啥盼头」 → 剥离「感觉/真/啥」+「没有→没」 → 「我活着没盼头」 → 命中
```

**边界把控**：只剥离语气/程度成分（什么、真的、太、好、有点、一直……），
承载否定与意图的字（不、没、想、要）一律保留。若把「了」也剥掉，
「我不想要这个作业了」就会被误判成危机——**误报比漏报更伤产品可信度**，
用户收到一次莫名其妙的危机干预，就再也不会说真话了。

### 验证

新增 `scripts/test_safety.py`：纯函数回归测试，不消耗 API 额度，可随时跑。

| 指标 | 结果 |
|---|---|
| 危机信号识别 | 21/21 |
| 普通表达误报 | 0/10 |
| 含「归一化匹配」命中的口语变体 | 4 条（词表里没有这些原句） |

同时跑完整评测：**7/7 场景通过**，空洞安慰率 0.0%、越界内容率 0.0%，无回归。
接口实测：「我觉得活着没什么意思」已正确返回 `blocked: true` 并给出热线；「这次考试考砸了」仍走正常共情流程。

### 经验

**关键词方案的问题不是「词不够多」，而是「匹配方式太死」。** 补词表是线性的工作量，
归一化把覆盖方式从「穷举说法」变成「归一化形式」——中文口语的变体主要在插入成分上，
这一层归一化的收益远大于继续堆词。当然天花板仍在，最终仍需语义模型兜底（见 README 已知局限）。

## 2026-10-11（第三轮）· 界面语音升级 + 危机后续机制修复

本轮共处理四项需求，其中第 3 项是**设计缺陷**，其余为体验与健壮性问题。

### 一、多个语音包可选（顶部选择）

原实现只自动挑选一个中文语音包，用户无法更换。改为：

1. 列出系统内全部中文语音包（含大陆、港台、粤语），标注「本机 / 在线」
2. 顶部语音条提供选择＋试听＋语速（慢/正常/快）
3. 选择结果写入 localStorage，下次打开自动恢复
4. 默认优先本地语音（响应更快、无网络依赖）

**取舍说明**：语音包由操作系统提供，不同机器上数量与音色不同，
因此界面不写死任何一款，而是把选择权交给用户，并在切换后立即试听以便当场判断。

### 二、界面观感优化

配色改为低饱和青绿 + 暖白渐变。**这不是纯审美选择**：使用场景多在情绪低落时，
高对比度与高饱和色会加剧紧绷感，因此刻意压低刺激强度，并加入呼吸光效、
更克制的圆角与阴影层次、移动端适配。

### 三、危机后续失忆（核心缺陷）

**现象**：用户说「我想自残」触发安全边界后，按话术回答「此刻心里最强烈的感觉是……」，
只要这句话不触发边界，智能体立刻回到日常语气，既不记得刚才的危机，也不再尝试挽回。

**根因**：`agent.chat()` 在危机分支里执行了 `self.history = []`。
原注释写的理由是「避免后续对话污染危机处理」——这个理由经不起推敲：
真正需要防的是「污染」，而清空历史连「记忆」一起删掉了，
结果就是危机干预退化成一次性弹窗。

**修复**（`src/agent.py` + `src/strategy.py` + `src/safety.py`）：

| 环节 | 修复内容 |
|---|---|
| 记忆 | 危机轮次如实写入历史（含固定话术本身），触发前内容同样保留 |
| 状态 | 新增 `crisis` 状态（类型 / 阶段 / 持续轮数），`reset()` 时清除 |
| 前 3 轮 | 「危机陪伴·持续关注」：表达担心、引用此前谈过的细节、确认当下安全 |
| 3 轮后 | 「危机陪伴·加力挽回」：更直接 + 一个当下可执行的具体行动要求 |
| 重复危机 | 升级话术，要求明确承诺，不再重复首次话术 |
| 退出 | 仅当用户明确表示安全时用固定话术收束并退出状态 |

**实测对话（第 3 轮那句是关键证据）**：

```
用户：这周考试考砸了，室友都比我强     → 反映与共情
用户：我想自残                        → 危机干预（固定话术）
用户：就是觉得压力很大，什么都做不好   → 危机陪伴·持续关注
      「我记得你之前提过考试和室友的事……此刻那种想伤害自己的念头，还在吗？」
用户：我也不知道                      → 危机陪伴·持续关注
用户：嗯                              → 危机陪伴·加力挽回（给出具体行动）
用户：我没事了，刚才是随口说的         → 危机收束并退出
用户：那聊聊别的吧                     → 恢复正常策略
```

**配套修复：否定语境识别**。测试用例暴露「我没有想自杀，别担心」曾被误判为危机
（否定词与关键词之间隔了「想」）。现改为向前最多看 4 字、允许否定词与关键词之间
只隔助动词；但「我是不是想死」仍按危机处理——那是疑问确认而不是否定，跳过才是漏报。

### 四、刷新 / 重新开始无响应

两个独立原因：

1. **会话过期后重置报 404**：`/api/reset` 遇到未知 sid 直接返回 404，前端未处理错误，
   界面看起来就是「点了没反应」。现改为服务端自动新建会话并返回新 sid，前端接过来继续用。
2. **前端缺少失败出口**：`/api/chat` 返回 `session_expired` 时前端会静默失败。
   现改为自动重建会话并**重放本轮消息**，用户无需任何操作；连接彻底失败时
   显示带「重试连接」按钮的说明卡片，并提示应通过服务地址而非 index.html 访问。

> 附带说明：「当前文件已被删除、移动或损坏」不是本项目的报错，
> 而是直接以静态文件方式打开 `index.html` 时预览环境给出的提示。
> 该文件是 Flask 模板，必须经 `web.py` 渲染才能工作——已在文档与错误卡片中明确写出。

|---|---|
| 安全边界回归（纯函数） | 识别 21/21、误报 0/13、安全声明 6/6、误判 0/4 |
| 危机流程专项测试 | 记忆保留 ✓ 持续关注 ✓ 加力挽回 ✓ 收束退出 ✓ 恢复正常 ✓ |

## 2026-10-11（第四轮）· 语音改为服务端在线合成：用户无需安装任何语音包

### 问题

上一轮把语音做成「浏览器本机语音 + 顶部可选语音包」，实测后暴露出前提性缺陷：
本机系统没有任何 TTS 语音包（注册表 SAPI / OneCore Tokens 均不存在），
于是下拉框空白、点试听无声。用户要听见声音，必须自己进系统设置下载语音包——
对「打开即用」的陪伴产品和答辩演示来说，这个门槛不可接受。

**根因不是代码写错，而是方案选错了前提**：Web Speech API 依赖操作系统语音引擎，
把可用性押在「用户机器装没装语音包」上，本身就是脆弱设计。

### 方案：服务端在线合成

新增 `src/tts.py`，用 edge-tts 调用微软语音服务生成 MP3，由 `/api/tts` 返回给前端播放。

| 维度 | 本机语音 | 服务端在线合成（新默认） |
|---|---|---|
| 用户需安装 | 需要（装不上就没解） | 完全不需要 |
| 音色 | 取决于系统，常见 0~2 个 | 固定 11 个中文音色（普通话/粤语/台湾，含性别与风格说明） |
| 离线 | 可用 | 不可用（断网自动降级到本机语音） |
| 成本 | 无 | 无（免费接口，不消耗 DeepSeek 额度） |

前端顶部新增「发音引擎」选择：在线语音（默认）/ 本机语音。本机无语音包时自动切回在线，
不再丢一个空白下拉框给用户。

### 四个实测暴露出的工程问题与解法

1. **朗读文本必须清洗**：TTS 会把 `**` 念成「星号星号」、把列表符号与 emoji 念出来。
   `clean_for_speech()` 剥离 Markdown / emoji，段落换行转句读；
   `010-82951332` 这类号码的连字符保留，仍读作号码。
2. **在线合成有约 2.4 秒固定开销**（主要是连接成本，与文本长短关系不大，
   实测 25 字与整段回复耗时接近）。解法是**首句预热**：对话接口返回回复时
   用后台线程先合成第一句，前端随后请求同一句直接命中缓存（实测 **3.8ms**）。
   注意只能热第一句——前端分句播放，热整段会与前端请求的缓存 key 不一致。
3. **分句流式播放**：回复按句切开，第一句合成完就出声，后续边播边取。
   前后端各有一份切句逻辑（`tts.split_sentences` / `splitSentences`），必须保持一致，
   否则预热对不上、各自合成一遍。
4. **同内容合成去重**：预热线程与前端请求可能同时到达。用 key 锁让后来者等待同一份结果，
   而不是合成两次（实测 3 个并发请求只做一次合成，返回字节完全一致）。

### 验证

| 项目 | 结果 |
|---|---|
| `/api/voices` 音色列表 | 11 个中文音色正常返回 |
| `/api/tts` 合成 | HTTP 200，`audio/mpeg`，47.6KB；音色切换与非法音色回退正常 |
| MP3 有效性 | 文件头校验通过 |
| 朗读清洗 | `**别急**，我们慢慢来。\n- 先深呼吸 😊` → `别急，我们慢慢来。先深呼吸` |
| 首句预热命中 | 3.8ms（未预热时约 2.4s） |
| 并发去重 | 3 个并发请求 2.5s 内全部返回相同 22896 字节 |
| 端到端 | 对话 → 取回复 → 合成该回复语音，HTTP 200 / 100KB |

### 经验

**依赖用户环境的方案，要在设计阶段就问一句「如果这个环境不具备，会怎样」。**
上一轮的实现本身没有 bug——它只是把可用性建立在一个很多机器上不成立的假设上。
把能力搬到服务端，付出的是「需要联网」，换回的是「任何设备打开都有声音」，
对于演示和分享场景这笔交换很划算。

同时，服务端方案自带一个成本项：**延迟**。合成不能像本机语音那样瞬时出声，
所以又引出预热、分句、去重三项优化。可见**换方案不是终点，新的约束会接着来**。

## 2026-10-11（第五轮）· 语气调制：让情绪被听得见

### 问题

语音上线后出现新问题：**一句话一个音色念到底**。
用户说「我想自残」和说「今天挺开心的」，声音毫无区别；
文字侧虽然换了危机话术，语气仍然平铺直叙。
验收反馈原话是「感觉若无其事」——在心理陪伴场景里，语气本身就是回应的一部分。

### 方案：一份情绪配置同时驱动文字与语音

新增 `src/emotion.py`，每轮由 `select_emotion()` 判定，输出两组参数：

1. **语音侧**：语速 / 音调 / 音量偏移 → TTS 引擎
2. **文字侧**：prompt_hint → 注入系统提示词，约束该轮情绪浓度

| 语气 | 触发 | 语速 | 音调 | 音量 |
|---|---|---|---|---|
| 警觉关切 alarm | 危机拦截 | −6% | −3Hz | +28% |
| 坚定陪伴 firm | 加力挽回 | −5% | −2Hz | +22% |
| 认真陪伴 watch | 持续关注 | −5% | −2Hz | +14% |
| 温柔安抚 gentle | 情绪很重 / 共情轮 | −8% | −3Hz | +6% |
| 沉稳承接 steady | 医疗边界 | −3% | −1Hz | +4% |
| 温和自然 warm | 日常默认 | −2% | 0 | +2% |
| 轻快明亮 bright | 情绪转好 | +5% | +5Hz | +5% |

### 三个设计取舍

1. **危机时变「慢、沉、响」，不是「快、高、响」**：高亢急促会让紧绷的人更慌；
   慢下来 + 更沉的音色 + 更用力，传达「我在认真对待」。**情绪浓度靠重量，不靠速度。**
2. **音调偏移限制 ±12Hz**：偏移过大会明显失真，听感变假反而削弱可信度。
3. **语气不能推翻用户偏好**：新增 `_combine_rate()`，把情绪语速的权重限制在
   用户自选语速幅度的一半以内——否则「用户选快 + 危机要慢」会互相抵消甚至反转。

### 写测试当场抓到两个 bug

新增 `scripts/test_emotion.py`（纯函数，不耗额度），首次运行就报出两处分支优先级写反：

- `crisis_closing`（用户已表示安全）被判成最高档危机语气，应为温柔的收束语气
- `medical_referral` 掉进日常语气，应为平实的沉稳语气

两类错误人工点界面很难发现（偶尔听到「语气不太对味」容易归因于错觉），
但断言一写就现形。修正后增加**力度阶梯断言**：音量必须单调递增
`warm < watch < firm < alarm`，危机语气音调必须比日常更沉——
「不能若无其事」从此是一条可回归的约束，而不是主观描述。

### 验证

| 项目 | 结果 |
|---|---|
| 情绪识别 | 9/9（含「前几天撑不住，现在好多了」正负混合句） |
| 各分支语气选择 | 12/12 |
| 语气参数合理性 | 通过（范围 + 阶梯单调性） |
| 音频差异 | 同一句话 7 种语气的 MP3 **指纹各不相同**，体积符合预期 |
| 端到端 6 轮 | `gentle → alarm → watch → watch → gentle(收束) → warm` |
| 安全边界回归 | 21/21 识别、0/13 误报（未受影响） |
| 完整评测 | **8/8 场景通过**，策略 8/8，空洞安慰 0%、越界 0% |

### 经验

**「情绪」在工程上必须被量化，否则无法保证也无法回归。**
把它翻译成 rate/pitch/volume 三个数字之后，两件事同时变简单了：
一是语音真的会变，二是「危机必须比日常更重」可以用断言守住。
如果停留在「让模型注意语气」这种描述上，评测永远测不到它。

## 2026-10-11（第六轮）· 语音延迟专项优化

### 反馈

「文字已经弹出了很长时间才开始播放语音，并且语音（正常）速度太慢，
等智能体说完用户可能早就看完文字了。」——两个抱怨，一个是延迟，一个是语速。

### 第一步：把延迟拆开量

不先量化就调参，等于猜。实测结果（这一轮所有数字都来自实测）：

| 观测项 | 实测 |
|---|---|
| 在线合成首字节 | 约 1.7~1.9 秒 |
| 与文本长度的关系 | **几乎无关**（`嗯。` 也要 1.78 秒，41 字也是 1.99 秒） |
| 首字节 → 整段传完 | 约 0.5 秒 |
| 并发 4 条合成总耗时 | 约 2.2 秒（**与 1 条几乎相同**） |
| 连接能否复用 | 否（连续三次调用首字节都在 1.7 秒上下，无改善） |

两个结论直接决定了改法：

1. **1.9 秒是云端启用的固有开销，压不动；但「等整段合成完」多等的那 0.5 秒是白等的。**
2. **并发几乎不增加耗时**，所以并行预取分句是免费的。

### 第二步：流式播放（省掉白等的 0.5 秒）

- `tts.stream_synthesize()`：用工作线程跑 asyncio，把云端返回的音频块推进队列，
  主生成器边取边 yield。客户端中途断开时 worker 仍会跑完并把**完整**音频写进缓存
  （只有完整才写缓存——否则会缓存一段被截断的话）。
- `/api/tts` 支持 GET，返回 chunked 响应（不设 Content-Length），
  浏览器直接以 `audio.src` 播放，边下边播。
- 前端从「fetch → Blob → 播放」改为「把地址交给 audio 元素」——
  **Blob 必须整段下载完才能播，这正是那 0.5 秒的来源。**

### 第三步：移除服务端预热（它已经变成拖累）

这是本轮最值得记的一处。原来的「后台预热第一句」上线后，前端请求与预热用的是
**同一个缓存键**，于是前端的流式请求被判定为「已有请求在合成」，排队等预热跑完——
结果又回到「整段合成完才有声音」。**同一个优化在旧方案里有用，在新方案里就有害。**

### 第四步：换引擎才是延迟的真正解（1.9s → 0.8s）

流式只能把 2.5 秒压到 1.9 秒。再往上，1.9 秒是云端启用本身，参数层面无解，
因此新增低延迟备选引擎（`tts.stream_fast()` / `fast_available()`）：

| 引擎 | 首字节 | 音色 | 情绪调制 |
|---|---|---|---|
| 极速语音（默认） | **809ms** | 较平实 | 仅语速 |
| 在线语音 | 1942ms | 11 个中文音色，自然 | 音调/音量/语速 |
| 本机语音 | 即时（本机通常无包） | 取决于系统 | 音调/语速 |

可用性由服务端实测（10 分钟缓存 + 启动时后台探测），不可用时前端自动退回在线语音，
并继续沿降级链处理（极速 → 在线 → 本机 → 明确提示）。

### 第五步：语速（另一个抱怨，独立于延迟）

1. **默认语速 1.0 → 1.25**，并迁移旧值（存的是旧默认值 1.0 时自动升级）——
   否则老用户仍是慢速，改了等于没改。
2. **语速改在播放端施加**（`playbackRate`，`preservesPitch`）而不是让服务端重新合成：
   改语速立即生效、不额外消耗一次约 2 秒的合成、也不让语速进入缓存键。
3. **按引擎折算听感系数**。这一步是量出来的：
   同一句话，极速引擎音频 6.9~7.9 秒、在线合成 5.1~5.5 秒，**平均比值 1.41**。
   极速引擎输出 64kbps、在线合成 48kbps，同样字数它本身念得更慢。
   不做补偿就会「出声更快、但念完更慢」，把省下的延迟又还回去。
   因此给极速引擎乘 1.4，保证换引擎时听到的语速一致。

### 第六步：让等待被看见

首音约 0.9 秒，虽短但仍需要说明。消息下方新增状态提示：
「🔊 语音准备中…」（慢速呼吸）→「🔊 朗读中」（律动条）→ 播放结束自动消失。
试听按钮则在合成期间进入加载态，避免用户反复点击。

### 验证

| 项目 | 改前 | 改后 |
|---|---|---|
| 文字出现 → 第一声 | 约 2500ms | **约 890ms** |
| 文字出现 → 首句可播完 | 约 2640ms | **约 1280ms** |
| 分句数（同一回复） | 3 段串行 | 3 段**并行**预取，句间无空档 |
| 缓存命中 | 3.8ms | 22ms（整段下发） |
| 安全边界回归 | 21/21、误报 0/13 | 未受影响 |
| 语气调制测试 | 9/9 + 12 分支 | 未受影响 |

### 经验

**「延迟高」不是一个可以靠调参解决的问题，必须先拆成可测量的几段。**
拆开之后才发现：真正的大头（1.9 秒）根本不在参数层面，而在选型层面；
而看起来最像瓶颈的那 0.5 秒，其实是「等整段下载完」这个实现细节造成的。
**能测量的部分才能优化，不能测量的部分只能换方案。**

另外，**优化会过期**：预热在旧方案里是对的，在流式方案里就是错的。
改架构时要回头检查那些基于旧假设的优化，否则它们会悄悄变成负收益。

## 第七轮 · 语音活人感 + 界面降噪 + 字体规范（2026-10-11 晚）

### 用户反馈

1. 语音不自然、不流畅，希望向豆包的听感看齐（语速、流畅度、音色，有"活人感"）。
2. 每条回复下方的「策略：xx · 语气：xx」小字是内部机制外泄，删掉；只在安全边界介入时保留「安全边界已介入」。
3. 字体统一为思源柔黑：气泡正文 Regular、顶部标题 Medium、底部快捷按钮 Regular。

### 问题诊断

**「不流畅」的真正来源不是音色，而是拆句方式。** 此前为压首响把回复逐句拆开、每句独立合成：
每句都会"新起一个调型"（合成引擎按句子起始计算韵律），句子之间又有 audio 元素切换的缝隙，
拼起来就是一顿一顿的"机器人念字"。句数越多越明显——这恰好和"分句能压首响"的目标相互打架。

### 改动

- **两段式合成**（index.html `splitChunks`）：第一段只取第一句保证尽快出声；剩余内容合并成
  一整段连续合成，句间停顿完全交给标点，节奏与真人一致。流式播放下第二段虽长，
  边合成边下发，第一句播完时早已就绪。实测 94 字整段首批可播仍为 1.88s（与短句相同，
  云端首字节开销与长度无关），总耗时 3.49s，无长度惩罚。
- **情绪音调放大**（web.py `_amplify_pitch`）：情绪定义的 pitch 偏移 ±3Hz 在合成结果里几乎不可闻，
  放大 1.8 倍并夹取在 ±12Hz 内，让"语气有情绪"在耳朵里成立，不再停留在纸面。
  本机引擎同步调整系数（/60 → /33）。
- **界面降噪**（index.html `addMsg`）：删除消息下方的策略/语气小字；
  仅 crisis 时显示「安全边界已介入」，不再外泄 crisis_interrupt 等内部代号。
- **字体规范**：引入思源黑体（Noto Sans SC 400/500，display=swap，本地黑体兜底）；
  正文与快捷按钮 400，顶部标题 500。
- 服务端 `split_sentences` 无调用方，更新注释说明两段式约定，避免误导后续维护。

### 验证

- JS / Python 语法检查通过；情绪 22/22、安全 34/34 回归通过
- alarm / warm 两种情绪合成 200 且音频体积正常；页面字体链接注入成功
- 首页与局域网地址均 200

### 修正（19:25）· 回退音色参数 + 修复极速引擎截断

用户反馈「这版语音更不自然了，换回之前那个语音包，语速没问题」。

**定位到两个问题叠加：**

1. 上一轮把回复改为「剩余内容合并成一整段」，而**极速引擎单次文本上限 180 字、超长直接截断**
   （`src/tts.py` 的 `_FAST_MAX_LEN`）。旧版逐句拆分时每句都短，从未暴露这个上限；
   合并成大段后，长回复被念到一半戛然而止——这比"不自然"更严重。
2. 上一轮新增的 `_amplify_pitch` 把情绪音调放大 1.8 倍，在线音色（晓晓）的音调被整体拉偏，
   听感偏离了原本的声音。

**修正**

- 回退 `_amplify_pitch`（web.py）与本机引擎的 pitch 系数（/33 → /60），音色参数恢复原值
- `splitChunks` 增加 maxLen 模式：极速引擎按 150 字切块（保守低于 180 上限），
  单句超长时硬切，保证每一块都不越界且内容零丢失
- `stream_fast` 的截断改为退到最近的句末标点，绝不念半个字
- 语速设置未改动（用户认可）

**验证**

| 项目 | 结果 |
|---|---|
| 切块单测 | 170 字 → 2 段、内容完整；400 字无标点单句 → 3 段、最大 150 |
| 语法检查 | JS / Python 通过 |
| 情绪 / 安全回归 | 22/22、34/34 |
| 页面 / fast 长文本合成 | 200 / 200（103KB） |

### 经验

**「上限」这类隐性约束，只有在输入规模变化时才会暴露。**
逐句改整段本身是合理优化，却踩中了极速引擎 180 字的硬限制——
旧行为（每句都短）掩盖了它，新行为（大段）放大了它。
改数据结构时，要回头检查下游对手里数据的**隐性假设**（长度、格式、条数）。

### 调整（19:35）· 默认引擎改回在线语音 + 语速微调

用户要求：「需要可以选择语音包的那一版的语音，语速相较于上一版稍微慢一点点」。

**改动**

- **默认引擎：极速 → 在线语音**。极速引擎是固定音色（下拉框被禁用），
  只有在线语音才谈得上「选语音包」；且它音色自然度明显更好。在线不可用才退回本机语音。
- **localStorage 键改名 `zhiyu_engine` → `zhiyu_engine_v2`**：旧实现会把
  「自动选择的结果」也写进 localStorage，直接改默认值永远不会生效——
  这是新默认值必须换键的原因，否则老用户仍会卡在极速引擎上。
- **语速 1.25 → 1.15**（「正常」档，慢约 8%）。同时把 1.0 / 1.25 都列为
  「历史默认值」参与迁移，确保没手动调过语速的老用户自动跟随新默认。
- 引擎下拉文案改为「极速语音（最快 · 音色固定）/ 在线语音（默认 · 音色可选）」，
  让取舍一眼可见。

**验证**：JS 语法通过；页面已含新配置；首页与局域网 200；在线晓晓合成 200（12KB）。

## 2026-10-11（第八轮）· 调用记录导出与文档一致性修订

### 用户诉求

「查找别人使用智能体的使用记录，给我他们与智能体的对话。」

### 调查过程

翻查 `logs/` 目录，共 6 段同学试用存档（另有 2 段作者本人命令行自测）：

| 备注 | 时间 | 轮数 | 备注 |
|---|---|---|---|
| 吴 | 10-10 13:40 | 7 | 唯一出现危机表述（当时**未**触发边界，词表漏检） |
| 路遥一梦 | 10-10 13:56 | 15 | 最长的一段 |
| （未填） | 10-10 14:05 | 6 | 用户连续三个试探性提问 |
| 吴2 | 10-11 16:12 | 7 | 考试考砸场景 |
| 吴3 | 10-11 20:30 | 1 | — |
| 吴4 | 10-11 20:53 | 3 | 与「吴2」同一开场句，回复长度差异明显 |

**顺带核实的一件事**：导出时逐条检查了 `blocked` 字段，**6 段共 39 轮的 `blocked` 全部为 `false`**——
包括「吴」那段说「我感觉想死」的第 6 轮。回看该轮日志，热线的写法是「400-161-9995」，
而当时代码里的话术模板写的是「12356 / 010-82951332」（已比对 10-10 的提交版本），
**两者对不上，说明那句回应是模型自己生成的，而不是系统拦截的结果**。

这与 10-10 已修复的危机词表漏检是同一件事——此前只在文档里定性描述，这次拿到了逐字段的原始证据。
**结论要写清楚：这 6 段记录里没有一次真正走上安全边界，安全边界的有效性不能拿这批数据来证明，只能拿回归测试（识别 21/21、误报 0/10）来证明。**

### 发现的机制缺陷：记录并非自动落盘

`ConversationLogger` 在**会话建立时**就已经挂在会话对象上（`web.py` 的 `_create_session`），
每轮对话也确实写进了 `logger.records`——**但 `save()` 只由 `/api/save` 这一个接口调用**，
而 `/api/save` 只有用户在页面上点「保存记录」并填备注时才会触发。

后果：

```
未点「保存记录」的会话 → 只存在内存 sessions 字典
                       → 2 小时 TTL 过期 / 服务重启 → 永久丢失
```

**也就是说，磁盘上的记录数 ≠ 实际试用人数。** 实际试过的同学远不止 6 位，
剩下的全部没有留下任何痕迹——而作业要求的恰恰是「让谁去试、试了什么、效果如何」的证据。

这与 Day 2 修掉的「对话轨迹只存在内存、退出即丢」是**同一类问题在同一处的复发**：
上次解决的是「进程退出前没人调用保存」，这次暴露的是「调用保存的主动权在用户手里」。

### 处理

1. **导出 `logs/试用对话全文.md`**：汇总全部 6 段同学试用的**逐句全文**（不是节选），
   含总览表、每段对话原文、从记录中能读出的结论、以及**明确写出数据局限**。
2. **修订统计口径**：`README.md` 与 `docs/成果汇总.md` 中的试用统计由「5 次」更正为
   「6 次 39 轮（同学试用）+ 2 次 17 轮（作者自测）」，并同步更新代码行数等数字。
3. **登记待补事项**：是否改为自动落盘，留给用户决定——因为它涉及
   **静默记录他人私密的情绪倾诉**，这不是一个可以替用户拍板的技术选择。

### 一个判断

这一轮没有改任何功能代码，但它比当天任何一次改动都更接近作业的核心要求。
前面 7 轮都在让智能体「更好用」，这一轮才让它的使用过程「可被看见」——
**做出来的东西有人用，和有证据证明有人用，是两件事。**

### 经验

**「谁来触发保存」决定了数据会不会存在。** 日志模块本身写得没错，
错在把触发的主动权交给了最不关心日志的人（试用者）。
设计留痕功能时，要先问一句：**这条记录真正需要的人，有没有能力让它产生？**
