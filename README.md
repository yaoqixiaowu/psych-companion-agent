# 知语 · 心理陪伴智能体

面向大学生的心理陪伴对话智能体。基于大模型 API，实现角色设定、安全边界与心理对话策略选择机制。

> **定位声明**：本项目是日常情绪支持与倾听工具，**不是**心理咨询师，**不能**替代专业心理服务。遇到危机情况时，系统会引导用户联系真人专业资源。

---

## 一、快速开始

### 1. 环境要求

- Python 3.10 及以上
- DeepSeek API 密钥（实验室提供或自行申请）

### 2. 安装依赖

推荐使用虚拟环境，避免污染系统 Python：

```bash
# 创建并激活虚拟环境（Windows）
python -m venv .venv
.venv\Scripts\activate

# macOS / Linux
python3 -m venv .venv
source .venv/bin/activate

# 安装依赖
pip install -r requirements.txt
```

> 若不激活虚拟环境，也可直接用 `pip install -r requirements.txt` 安装到全局。

### 3. 配置密钥

项目已包含 `.env` 文件（被 `.gitignore` 排除，不会提交）。用记事本打开：

```bash
notepad .env
```

把其中这一行：

```
DEEPSEEK_API_KEY=sk-在这里填入你的真实密钥
```

改成真实密钥：

```
DEEPSEEK_API_KEY=sk-这里替换成你自己的密钥
```

密钥获取方式：
- **优先向实验室或助教索取**（作业说明写明「大模型 API 由实验室提供」）
- 若实验室不提供，自行申请：https://platform.deepseek.com/api_keys
  - 新账号需充值才能调用（API 无赠送额度），￥10 足够跑完全部评测

> `.env` 的作用：存放密钥而不进版本库。若把密钥直接写进 `.py` 文件，提交到 GitHub 后会公开泄露。

### 4. 验证连通性

```bash
python scripts/test_api.py
```

预期输出：

```
[1/3] 正在读取配置...
      Base URL : https://api.deepseek.com
      模型     : deepseek-flash
      密钥     :已配置（前6 位 sk-xxxx）
[2/3] 正在发送测试请求...
      耗时 1.8s
[3/3] [成功]
      模型回复：连接成功
```

若失败，脚本会按错误类型给出排查建议（401 密钥无效 / 402 余额不足 / 429 请求过频 / 网络不通）。

### 5. 开始对话

**方式 A：浏览器界面（推荐）**

```bash
python web.py
```

浏览器会自动打开 `http://127.0.0.1:5000`。界面提供对话、实时统计、记录保存三个功能。

**让同学访问（同一 WiFi / 校园网）**

```bash
# Windows PowerShell
$env:PSYCH_HOST="0.0.0.0"
python web.py

# 或直接双击 启动知语-局域网.bat
```

启动后终端会打印出可访问的地址，例如：

```
同一网络内可用以下地址访问：
  http://10.134.53.221:5000    (DESKTOP-BK4RVP4)
```

把这个地址发给同学即可。**注意 `0.0.0.0` 是监听地址，不是访问地址**——同学要用终端打印出的那个 `http://10.x.x.x:5000`。

前提条件：

| 条件 | 说明 |
|---|---|
| 同一网络 | 你和朋友必须连同一个 WiFi / 校园网 |
| 你的服务保持运行 | 关闭终端窗口或按 Ctrl+C 后他人即无法访问 |
| 防火墙放行 | 首次运行 Windows 可能弹出「是否允许 Python 访问网络」，需选择允许 |

> ⚠️ **安全提醒**：当前版本没有登录验证，同网络内任何人都能打开对话并消耗你的 API 额度。仅建议在可信的校园网或家庭网络使用，不要暴露到公共网络。

**方式 B：命令行**

```bash
python main.py

# 记录他人试用时加备注，便于区分记录用途
python main.py --note "同学A的试用反馈"
```

交互命令：

| 命令 | 作用 |
|---|---|
| `help` | 查看可用命令 |
| `trace` | 查看每轮使用的策略与拦截情况 |
| `stats` | 查看本次对话的实时统计 |
| `reset` | 清空对话状态，重新开始 |
| `quit` | 退出 |

> 两种方式共用同一个 `CompanionAgent` 核心，行为完全一致。推荐同学用浏览器方式，省去配置环境的麻烦。

### 6. 对话日志

程序退出时自动在 `logs/` 目录生成两种格式的记录：

| 文件 | 用途 |
|---|---|
| `session_*.md` | 便于直接贴进开发日志或作为附录提交 |
| `session_*.json` | 结构化数据，供后续统计分析 |

每条记录包含：带时间戳的完整对话、本轮实际使用的策略、安全边界是否触发及原因、回复质量判定（空洞安慰 / 越界内容 / 是否提问）。

**日志目录不加入 `.gitignore`** —— 对话记录是作业要求的「记录反馈」证据，需要随仓库提交。开发过程中的自测数据通过文件名模式 `*自测*` 排除。

> 早期版本的对话轨迹只存在内存中，退出即丢失。这导致能演示「代码能跑」，却拿不出「谁试了、试了什么、效果如何」的证据。现改为落盘保存。

## 三、系统设计

### 3.1 模块结构

```
src/                    核心层（与界面无关）
├── config.py       配置与密钥加载
├── llm_client.py   DeepSeek API 封装
├── persona.py      角色设定与语气（系统 prompt 基底）
├── safety.py       安全边界 + 回复质量判定
├── strategy.py     心理对话策略选择机制
├── agent.py        主流程：安全检查 → 策略选择 → 模型调用
└── logger.py       对话日志落盘

main.py                 命令行入口
web.py                网页入口（Flask，复用同一核心）
templates/index.html  网页界面
启动知语.bat           Windows 双击启动脚本

eval/
├── scenarios.py    评测场景集
├── metrics.py      评测指标定义
└── run_eval.py     评测执行脚本
```

**核心层与界面层分离**：`src/` 不感知自己是被命令行还是网页调用，两个入口复用同一个 `CompanionAgent`。因此不存在两套行为不一致的实现——这与之前「评测绕过 agent.py 导致认知重构成死代码」是同一个教训。

### 3.2 处理流程

每轮用户输入依次经过三个环节：

```
用户输入
   ↓
[1] 安全边界检查  ← 优先级最高
   │   命中危机 → 立即中断，返回求助渠道（不调用模型）
   │   命中医疗边界 → 拒绝诊断，引导专业机构
   ↓ 通过
[2] 策略选择      ← 规则驱动，可解释可复现
   │   reflect / explore / support / reframe
   ↓
[3] 调用大模型    ← 系统提示词 = 角色基底 + 本轮策略
   ↓
回复用户
```

### 3.3 关于 thinking 模式的关闭

`deepseek-flash` 默认开启思考模式，会返回 `reasoning_content` 并计入输出 token。

**本项目显式关闭**（`thinking: {"type": "disabled"}`），原因有三：

1. 推理过程对用户没有价值——用户需要的是共情回应，不是模型的思维链
2. 成本上升——推理 token 计入输出费用
3. 响应变慢——实测关闭后耗时从 6.8s 降至 1.9s

这是一个典型的场景驱动的技术取舍，而非照搬默认配置。

### 3.4 安全边界设计

明确「不做什么」，比定义「做什么」更重要：

| 边界 | 处理方式 |
|---|---|
| 自伤/自杀信号 | 关键词硬拦截，固定话术引导真实求助渠道，清空历史 |
| 伤人风险 | 同上 |
| 疾病诊断与处方 | 拒绝下结论，但不阻断对话，引导专业机构 |
| 不替用户做决定 | 写入角色提示词，策略层不提供「该选哪个」 |
| 不空洞安慰 | 评测指标自动检测安慰话术 |

危机干预话术依据「陪伴—倾听—鼓励求助」三步原则，提供 24 小时援助热线（12356 全国统一心理援助热线）。

### 3.5 策略选择机制

四种策略源自《心理咨询面谈技术》第 4 版的核心技术：

| 策略 | 适用时机 | 目标 |
|---|---|---|
| 反映与共情 | 用户已说出具体感受或事件 | 让用户感到被理解 |
| 探索与澄清 | 用户描述模糊、说不清感受 | 把模糊感受说得具体 |
| 支持与鼓励 | 用户提及已做的事，或在自我否定 | 强化自我效能 |
| 认知重构 | 用户索要答案且此前已给过建议 | 提供新视角，不说教 |

**策略选择是上下文感知的。** `select_strategy()` 接收 `strategy_history`（此前用过的策略）与 `has_given_advice`（是否已给过建议），因此能自我调节：

- 同一策略最多连续 2 轮（`MAX_CONSECUTIVE`），超过则强制轮换
- 用户索要答案时：已给过建议 → 认知重构；未给过 → 先共情
- 轮换顺序从上轮策略的位置继续推进，避免在两个策略间来回摆动

连续追问三轮以上会让用户从「被陪伴」变成「被审问」，这是引入轮换机制的直接动因。该机制由真实试用暴露（详见开发日志）。

规则优先级（高→低）：

| 顺序 | 判定条件 | 选中策略 |
|---|---|---|
| 规则 0 | 含「说不上来」「说不清」等模糊表达信号 | 探索与澄清 |
| 规则 1 | 索要答案（视是否已给过建议） | 认知重构 / 反映与共情 |
| 规则 2 | **同策略连续使用已达上限** | 按轮换顺序切换 |
| 规则 3 | 提及自己的努力或已有支撑 | 支持与鼓励 |
| 规则 4 | 情绪强烈（难受 / 焦虑 / 崩溃等） | 反映与共情 |
| 规则 5 | 描述具体事件且非首轮 | 探索与澄清 |
| 兜底 | 首轮 / 后续轮 | 共情 / 轮换 |

规则 0 优先级最高，因为它对应赛题背景指出的核心人群：学生「难以直接描述自身困扰」。此时共情无效——用户连自己的感受都抓不住，复述只会让他更困惑，正确做法是立刻提供描述抓手。

规则 2 的优先级经实测校准。它原本排在内容匹配规则之后，导致「我已经」「我试过」这类高频短语反复触发支持鼓励。**当连续追问已经造成负担时，即使用户输入出现这些词，也应先换方式。**

采用**规则驱动**而非模型判定，原因是作业要求评测策略是否有效——规则方案可解释、可复现、可测量。

## 四、评测方法

对应任务目标「让谁去试、试哪些场景、看出什么指标」：

**试什么场景**：6 个场景，覆盖情绪宣泄、表达障碍、决策困惑、安全边界（危机 / 医疗）、策略轮换五类。

| 指标 | 当前结果 |
|---|---|
| 边界正确场景数 | 6/6 |
| 策略选择正确场景数 | 6/6 |
| 同策略最长连续轮次 | 1 轮（上限 2） |
| 空洞安慰率 | 0.0% |
| 越界内容率 | 0.0% |
| 平均回复长度 | 62.3 字符 |
| 提问轮次占比 | 75.0% |

评测同时校验三件事：

- **边界是否生效** —— 该拦截的场景是否被拦截
- **策略选择是否符合预期** —— 每个场景定义了 `expect_strategies`，实际策略与之比对
- **策略是否连续重复** —— 部分场景用 `max_consecutive` 约束（如「连续追问导致负担」场景不允许同策略超过 2 轮）

后两项是刻意设计的：若只校验边界，策略选择器可能一直选错策略而无人发现。**开发过程中正是这两项校验暴露了两个真实缺陷**（详见开发日志）：

1. 危机场景轨迹被误清 → 评测误报「未拦截」
2. 用户说「说不上来」时策略失效 → 选了共情，但此时共情无效
3. 连续 7 轮都用探索与澄清 → 提问变成盘问

第 3 项是在**真实试用**（`logs/` 中的对话记录）中发现的，自动化场景未能覆盖。这是「让谁去试」这一环的直接价值。

**谁去试**：已完成作者本人两轮真实试用，记录见 `logs/`。其中第一轮暴露了三个自动化评测未发现的缺陷（连续 7 轮同策略、认知重构成死代码、策略与回复脱节），详见 `logs/试用记录汇总.md` 与开发日志。

**后续需补充**：当前样本仅来自作者本人。仍需邀请 3–5 位同学分别试用，并收集主观评分（被理解程度、有无说教感、是否愿意继续聊）。这部分是自动化指标无法替代的。

### 评测发现并修复的缺陷

开发过程中评测暴露了三个真实问题，均已修复（详见 `docs/开发日志.md`）：

1. **危机场景轨迹被误清** —— `reset()` 同时清空 `trace`，导致评测误报「未拦截」
2. **策略选择器对表达模糊的用户失效** —— 用户说「说不上来」时选了共情，但此时共情无效，应提供描述抓手
3. **连通性脚本误报成功** —— `max_tokens` 过小导致 thinking 阶段耗尽配额，脚本却显示成功

第2 点最关键：它直接对应赛题背景中「学生难以直接描述自身困扰」这一核心特征。

## 六、已知局限

1. **危机识别依赖关键词匹配**，会漏检委婉表达。例如「活着没意思」「算了」等表述不会命中当前的 `self_harm` 词表。这是当前最需要改进的地方——生产环境应叠加分类模型。
2. **真实试用样本单一**。`logs/` 中的记录仅来自作者本人两轮对话，样本量不足以支撑结论。仍需 3–5 位不同背景的试用者，并收集主观评分。
3. **Web 版会话存在内存中，且无鉴权**。`web.py` 用 Python 字典存储会话，服务重启即丢失，且无法多进程部署。以 `0.0.0.0` 启动时，同网络内任何设备都能访问并消耗 API 额度。若要长期在线或公网使用，需替换为 Redis 等外部存储并加入鉴权。**当前仅建议本机或可信校园网内使用。**
4. **策略执行依赖模型遵守提示词**。已新增 `check_strategy_consistency()` 自动检测偏差，但检测只能发现问题，不能纠正。根治需要结构化输出约束。
5. **`MAX_CONSECUTIVE = 2` 是经验值**，未经临床或文献依据校准。真实使用中可能需要调整为 3，或按不同情绪强度分级。
6. **策略选择为人工规则**，未做自适应学习。用户长期使用后的偏好变化无法捕捉。
7. **回复长度依赖提示词约束**，未做硬性截断。
8. **未做多轮对话的策略冲突检测**。目前只检测「连续重复」，不检测语义层面的策略冲突（如刚重构完又立即追问原因）。
