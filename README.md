# 知语 · 心理陪伴智能体

面向大学生的心理陪伴对话智能体。基于大模型 API，实现角色设定、安全边界与心理对话策略选择机制。

> **定位声明**：本项目是日常情绪支持与倾听工具，**不是**心理咨询师，**不能**替代专业心理服务。遇到危机情况时，系统会引导用户联系真人专业资源。

### 界面与语音功能（2026-10-11 更新）

- **界面**：安静、低刺激的配色（减少情绪紧绷感）、消息动画、打字中提示、快捷开场、移动端适配
- **语音朗读（无需用户安装任何语音包）**：三档引擎可在顶部切换，**在线语音**（**默认**，11 个中文音色可选，
  音色最自然，首音约 1.9 秒）、**极速语音**（首音约 0.8 秒，但音色固定、听感较平实）、**本机语音**（离线兜底）。
  语速可调（默认「正常」档 = 1.15）、可试听，选择自动记住；引擎不可用时自动沿降级链退回。详见 3.7 与 3.9 节
- **语音延迟已专项优化**：流式边合成边播、分句并行预取、播放端变速。
  实测「文字出现 → 第一声」由约 2500ms 降到 **约 890ms**，详见 3.9 节
- **语气随情绪变化**：系统每轮判定用户情绪与安全状态，自动调整声音的**语速/音调/音量**
  （危机时更慢、更沉、更用力），并同步约束该轮文字的情绪浓度。共 8 档语气，详见 3.8 节

- **危机后持续关注**：安全边界触发后不会「忘记」——后续轮次保持安全关注语气，并在多轮未缓解时加力挽回，详见 3.6 节

## 一、快速开始

### 1. 环境要求

- Python 3.10 及以上
- DeepSeek API 密钥（实验室提供或自行申请）

### 2. 安装依赖

**推荐：什么都不用装。**

项目根目录带有一个自包含的运行环境 `.venv-local` 和三个启动脚本，双击即可：

| 脚本 | 用途 |
|---|---|
| `启动知语-局域网.bat` | **演示 / 答辩用**，同一 WiFi 内的同学都能打开 |
| `启动知语.bat` | 只有本机能打开，最安全 |
| `修复运行环境.bat` | 换电脑、或拷到 U 盘带到别的机器后打不开时，先双击它 |

脚本会**实际探测**解释器（跑一次 `import flask`）再决定用哪个，不只看文件是否存在；
端口被占用时会自动把上一个服务关掉再启动。

**手动安装（仅当需要自己配环境时）**

```bash
python -m venv .venv-local
.venv-local\Scripts\activate        # macOS / Linux: source .venv-local/bin/activate
pip install -r requirements.txt
```

> ⚠️ 注意：仓库里的 `.venv` 是在**另一台机器上创建的**（`pyvenv.cfg` 指向 `C:\Users\wuxiangping`），
> 在这台机器上不可用。请使用 `.venv-local`，或按上面的命令新建一个。运行脚本时用
> `.venv-local\Scripts\python.exe web.py`。

  - 新账号需充值才能调用（API 无赠送额度），￥10 足够跑完全部评测

> `.env` 的作用：存放密钥而不进版本库。若把密钥直接写进 `.py` 文件，提交到 GitHub 后会公开泄露。

### 5. 开始对话

**方式 A：浏览器界面（推荐）**

```bash
python web.py
```

浏览器会自动打开 `http://127.0.0.1:5000`。界面提供对话、实时统计、记录保存三个功能。

**让同学访问（同一 WiFi / 校园网）**

**最简单的方式：双击 `启动知语-局域网.bat`**

会出现一个黑色命令行窗口，显示可访问的地址：

```
同一网络内可用以下地址访问：
  http://10.134.53.221:5000    (你的电脑名)
```

把这个地址发给同学即可。

**关键：这个窗口要一直开着。** 它是服务主进程，关闭窗口 = 停止服务，其他人将无法访问。

也可以用命令行：

```bash
# Windows PowerShell
$env:PSYCH_HOST="0.0.0.0"
python web.py

# Linux / macOS
PSYCH_HOST=0.0.0.0 python web.py
```

前提条件：

| 条件 | 说明 |
|---|---|
| 同一网络 | 你和朋友必须连同一个 WiFi / 校园网 |
| 保持窗口开启 | 关闭启动窗口后他人即无法访问 |
| 防火墙放行 | 首次运行 Windows 可能弹出「是否允许 Python 访问网络」，需选择允许 |

> ⚠️ **安全提醒**：当前版本没有登录验证，同网络内任何人都能打开对话并消耗你的 API 额度。仅建议在可信的校园网或家庭网络使用，不要暴露到公共网络。

**方式 B：命令行**

```bash
python main.py

# 记录他人试用时加备注，便于区分记录用途
python main.py --note "同学A的试用反馈"
```

交互命令：

| 命令 | 作用 |
|---|---|
| `help` | 查看可用命令 |
| `trace` | 查看每轮使用的策略与拦截情况 |
| `stats` | 查看本次对话的实时统计 |
| `reset` | 清空对话状态，重新开始 |

### 6. 对话日志

落盘后会在 `logs/` 目录生成两种格式的记录：

| 文件 | 用途 |
|---|---|
| `session_*.md` | 便于直接贴进开发日志或作为附录提交 |
| `session_*.json` | 结构化数据，供后续统计分析 |

**两个入口的落盘方式不同，这点很关键：**

| 入口 | 何时落盘 |
|---|---|
| 命令行 `main.py` | 退出时**自动**落盘 |
| 网页 `web.py` | ⚠️ **只有用户主动点页面上的「保存记录」并填备注才落盘** |

> 网页版不点「保存记录」的话，对话只存在服务器内存里（`web.py` 的 `sessions` 字典），
> **2 小时不活动（TTL）或被重启即永久丢失**。
> 所以邀请同学试用时，**记得提醒对方点一下「保存记录」**——否则这段对话不会被留下，
> 也就拿不出「谁试了、试了什么」的证据。

每条记录包含：带时间戳的完整对话、本轮实际使用的策略、安全边界是否触发及原因、回复质量判定（空洞安慰 / 越界内容 / 是否提问）。

**日志目录不加入 `.gitignore`** —— 对话记录是作业要求的「记录反馈」证据，需要随仓库提交。开发过程中的自测数据通过文件名模式 `*自测*` 排除。

> 早期版本的对话轨迹只存在内存中，退出即丢失。这导致能演示「代码能跑」，却拿不出「谁试了、试了什么、效果如何」的证据。现改为落盘保存。
>
> **但网页版仍有一个缺口**：落盘的主动权在使用者手上（要靠对方点「保存记录」）。
> 2026-10-11 导出试用记录时确认了这一点——**磁盘上的记录数会明显少于实际试用人数**。
> 是否改为自动落盘，已登记在 `docs/成果汇总.md` 的待补事项中。

## 三、系统设计

### 3.1 模块结构

```
src/                    核心层（与界面无关）
├── config.py       配置与密钥加载
├── llm_client.py   DeepSeek API 封装
├── persona.py      角色设定与语气（系统 prompt 基底）
├── safety.py       安全边界 + 回复质量判定
├── strategy.py     心理对话策略选择机制
├── agent.py        主流程：安全检查 → 策略选择 → 模型调用
└── logger.py       对话日志落盘

main.py                 命令行入口
web.py                网页入口（Flask，复用同一核心）
templates/index.html  网页界面
启动知语.bat           Windows 双击启动脚本

eval/
├── scenarios.py    评测场景集
├── metrics.py      评测指标定义
└── run_eval.py     评测执行脚本
```

**核心层与界面层分离**：`src/` 不感知自己是被命令行还是网页调用，两个入口复用同一个 `CompanionAgent`。因此不存在两套行为不一致的实现——这与之前「评测绕过 agent.py 导致认知重构成死代码」是同一个教训。

### 3.2 处理流程

每轮用户输入依次经过三个环节：

```
用户输入
   ↓
[1] 安全边界检查  ← 优先级最高
   │   命中危机 → 立即中断，返回求助渠道（不调用模型）
   │   命中医疗边界 → 拒绝诊断，引导专业机构
   ↓ 通过
[2] 策略选择      ← 规则驱动，可解释可复现
   │   reflect / explore / support / reframe
   ↓
[3] 调用大模型    ← 系统提示词 = 角色基底 + 本轮策略
   ↓
回复用户
```

### 3.3 关于 thinking 模式的关闭

`deepseek-flash` 默认开启思考模式，会返回 `reasoning_content` 并计入输出 token。

**本项目显式关闭**（`thinking: {"type": "disabled"}`），原因有三：

1. 推理过程对用户没有价值——用户需要的是共情回应，不是模型的思维链
2. 成本上升——推理 token 计入输出费用
3. 响应变慢——实测关闭后耗时从 6.8s 降至 1.9s

这是一个典型的场景驱动的技术取舍，而非照搬默认配置。

### 3.4 安全边界设计

安全设计的依据来自竞品调研中查到的真实事故，详见 `docs/竞品调研.md`。核心结论是：**安全必须由代码保证，不能依赖模型的善意判断。**

| 边界 | 处理方式 |
|---|---|
| 自伤/自杀信号 | 关键词硬拦截，固定话术引导真实求助渠道，清空历史，**不调用模型** |
| 伤人风险 | 同上 |
| 疾病诊断与处方 | 拒绝下结论，但不阻断对话，引导专业机构 |
| 不替用户做决定 | 写入角色提示词，策略层不提供「该选哪个」 |
| 不空洞安慰 | 评测指标自动检测安慰话术（8 个词表） |
| 不制造依赖 | 不设计任何让 AI「显得需要用户」的互动 |

危机干预话术依据「陪伴—倾听—鼓励求助」三步原则，提供 24 小时援助热线（12356 全国统一心理援助热线）。

> **这条设计来自真实教训。** Replika 早期曾出现用户询问「我应该割伤自己吗」、AI 回答「应该」的案例；Character.AI 在 2024 年因 14 岁少年与其角色长期对话后死亡而面临多起诉讼与FTC 调查，调查材料显示**公司已知风险但优先考虑参与度指标**。
>
> 前者说明模型在诱导下会给出灾难性回应；后者说明**依赖诱导是被商业指标主动放大的风险**。两者的共同教训是：安全不能交给模型或商业目标，必须由代码强制执行。

### 3.5 策略选择机制

四种策略源自《心理咨询面谈技术》第 4 版的核心技术：

| 策略 | 适用时机 | 目标 |
|---|---|---|
| 反映与共情 | 用户已说出具体感受或事件 | 让用户感到被理解 |
| 探索与澄清 | 用户描述模糊、说不清感受 | 把模糊感受说得具体 |
| 支持与鼓励 | 用户提及已做的事，或在自我否定 | 强化自我效能 |
| 认知重构 | 用户索要答案且此前已给过建议 | 提供新视角，不说教 |

**策略选择是上下文感知的。** `select_strategy()` 接收 `strategy_history`（此前用过的策略）与 `has_given_advice`（是否已给过建议），因此能自我调节：

- 同一策略最多连续 2 轮（`MAX_CONSECUTIVE`），超过则强制轮换
- 用户索要答案时：已给过建议 → 认知重构；未给过 → 先共情
- 轮换顺序从上轮策略的位置继续推进，避免在两个策略间来回摆动

连续追问三轮以上会让用户从「被陪伴」变成「被审问」，这是引入轮换机制的直接动因。该机制由真实试用暴露（详见开发日志）。

规则优先级（高→低）：

| 顺序 | 判定条件 | 选中策略 |
|---|---|---|
| 规则 0 | 含「说不上来」「说不清」等模糊表达信号 | 探索与澄清 |
| 规则 1 | 索要答案（视是否已给过建议） | 认知重构 / 反映与共情 |
| 规则 2 | **同策略连续使用已达上限** | 按轮换顺序切换 |
| 规则 3 | 提及自己的努力或已有支撑 | 支持与鼓励 |
| 规则 4 | 情绪强烈（难受 / 焦虑 / 崩溃等） | 反映与共情 |
| 规则 5 | 描述具体事件且非首轮 | 探索与澄清 |
| 兜底 | 首轮 / 后续轮 | 共情 / 轮换 |

规则 0 优先级最高，因为它对应赛题背景指出的核心人群：学生「难以直接描述自身困扰」。此时共情无效——用户连自己的感受都抓不住，复述只会让他更困惑，正确做法是立刻提供描述抓手。

规则 2 的优先级经实测校准。它原本排在内容匹配规则之后，导致「我已经」「我试过」这类高频短语反复触发支持鼓励。**当连续追问已经造成负担时，即使用户输入出现这些词，也应先换方式。**

采用**规则驱动**而非模型判定，原因是作业要求评测策略是否有效——规则方案可解释、可复现、可测量。

### 3.6 危机后续机制（2026-10-11 修复）

**问题**：早期版本在触发安全边界后清空对话历史，理由是「避免后续对话污染危机处理」。
实测证明这个理由不成立，反而制造了更严重的问题——

用户在危机话术之后回答一句不触发边界的话（例如「就是觉得很累」），
智能体立刻回到日常语气，既不知道刚刚发生过危机，也忘了触发前用户说过的内容。
**危机干预被处理成一次性的弹窗，而不是一段持续的陪伴。**

**修复后的机制**：

| 环节 | 处理方式 |
|---|---|
| 记忆 | 危机轮次如实写入对话历史（含固定话术本身），触发前的内容同样保留 |
| 状态 | 新增危机后续状态 `crisis`，记录类型、阶段与持续轮数 |
| 前 3 轮 | 使用「危机陪伴·持续关注」策略：明确表达担心、确认当下安全、引用此前谈过的细节 |
| 3 轮后未缓解 | 切换「危机陪伴·加力挽回」：更直接地表达担心，提出当下可执行的具体行动要求 |
| 重复危机 | 使用升级话术 `CRISIS_RESPONSE_ESCALATED`，要求一个明确的承诺，而非再次重复首次话术 |
| 退出 | 仅在用户**明确**表示安全时（`declares_safety`）用固定话术收束，随后恢复正常策略 |

「退出条件必须由用户明确给出」是这条设计的关键：把含糊的「没什么」当作安全，
就是拿用户的安全赌运气；反之，用户已经明确表示安全却继续用危机语气，会让他感到被审问。

与之配套，匹配层新增**否定语境识别**：`我不想死，我只是太累了` 不再被误判为危机信号，
但 `我是不是想死` 仍按危机处理——后者不是否定，而是疑问确认，跳过它才是漏报。

> **这条修复来自验收前的自查。** 开发日志记录：自动化评测 7/8 场景全部通过时，
> 这个缺陷依然存在——因为原有场景的危机用例只有一轮，没有覆盖「危机之后会怎样」。
> 新增场景「危机后的持续关注」（逐轮期望拦截状态）后，该缺陷才被固化为例行回归项。

### 3.7 语音引擎：为什么放在服务端（2026-10-11 追加）

最初用浏览器自带的 Web Speech API 做朗读，实现后才发现一个被忽略的前提：
**它依赖操作系统安装过语音包**。开发机（精简版 Windows）一个中文语音都没有，
页面上语音下拉框是空的、点了也没声音——用户得自己进系统设置下载语音包才能听见。
对一个「打开即用」的陪伴产品来说，这个门槛不可接受，也让答辩演示多了一个不确定因素。

因此改为**服务端合成**（`src/tts.py`，基于 edge-tts 调用微软语音服务）：

| 维度 | 本机语音（Web Speech API） | 服务端在线合成 |
|---|---|---|
| 用户是否需安装 | **需要**，且装不上就没解 | **完全不需要**，打开即有声 |
| 可用音色 | 取决于系统，常见 0~2 个 | 固定 11 个中文音色，可选性别/风格/方言 |
| 离线可用 | 是 | 否（断网自动降级到本机语音） |
| 额外成本 | 无 | 无（免费接口，不消耗 DeepSeek 额度） |

**工程细节**（都是实测暴露出来的问题，不是设想）：

1. **朗读前清洗文本**：TTS 会把 `**` 念成「星号星号」、把列表符号和 emoji 念出来。
   `clean_for_speech()` 剥离 Markdown 与 emoji，段落换行转成句读停顿；
   号码中的连字符保留，`010-82951332` 仍读作号码。
2. **分句播放**：回复按标点切成片段，逐句合成与播放。
   切句逻辑在前后端各有一份，必须保持一致（`tts.split_sentences` 与 `splitSentences`）。
3. **同内容合成去重**：同一句话可能被并发请求，用 key 锁让后来者等待同一份结果，
   而不是重复向云端发起合成（实测 3 个并发请求只做一次合成，结果字节完全一致）。
4. **失败不阻断**：合成失败返回可识别错误码，前端按降级链处理；不影响文字对话本身。

> 注：本节原有一条「后台预热第一句」的优化，已在 2026-10-11 的延迟优化中**移除**，
> 原因见 3.9 节——流式播放上线后，预热反而会让前端请求排队等它完成，得不偿失。

### 3.9 语音延迟优化：从「等整段合成完」到「边合成边播」（2026-10-11 追加）

上线后收到的反馈很具体：**文字早就弹出来了，声音要等很久才响；而且念得太慢，
文字都读完了声音还在念前半句。** 这不是感觉问题，量化后能看清每一段耗时：

| 观测项 | 实测 |
|---|---|
| 在线合成首字节 | **约 1.7~1.9 秒** |
| 首字节与文本长度的关系 | **几乎无关**（念 2 个字与念 41 个字一样久） |
| 首字节 → 整段传完 | 约 0.5 秒 |
| 并发 4 条合成的总耗时 | 约 2.2 秒（与 1 条几乎相同） |

由此得到两个结论，也决定了改法：

**结论一：1.9 秒是不可压缩的连接/云端启用开销，但 0.5 秒可以被省掉。**
原先的实现等**整段**合成完才返回，等于白白多等那 0.5 秒。于是：

1. **改为流式下发**（`/api/tts` 支持 GET + chunked 响应，`tts.stream_synthesize()`）。
   云端是一块块吐音频的，服务端取到一块就转发一块，浏览器边下边播 →
   首音从约 2.5 秒提前到约 1.9 秒。
2. **移除服务端预热**。预热与前端播放请求用的是同一段内容（同一个缓存键），
   于是前端请求会被判定为「已有请求在合成」而排队等预热完成，
   结果反而退化成「等整段合成完才有声音」——**这项优化在流式上线后从帮忙变成了拖后腿**。
3. **分句并行预取**：所有分句的音频元素在开头一次性建好、同时开始合成，
   顺序播放。这样第一句在播时后面的句子早已就绪，句间没有空档
   （并发代价可忽略，见上表第 4 行）。

**结论二：延迟的瓶颈是「云端启用」，换引擎比调参数有效。**
再优化也只能在 1.9 秒附近打转，因此增加一个**低延迟备选引擎**：

| 引擎 | 首字节 | 音色 | 情绪调制 | 说明 |
|---|---|---|---|---|
| **极速语音** | **约 0.8 秒** | 较平实 | 仅语速 | 第三方公开朗读接口，**延迟最低，默认使用** |
| 在线语音 | 约 1.9 秒 | 自然（11 个中文音色） | 音调/音量/语速 | 音质优先，可在顶部切换 |
| 本机语音 | 即时（但通常无语音包） | 取决于系统 | 音调/语速 | 离线兜底 |

极速引擎的可用性由服务端**实测**（该接口可能被网络屏蔽），不可用时前端自动退回在线语音，
并沿降级链继续处理（极速 → 在线 → 本机 → 明确提示）。

**语速**：默认从 1.0 提到 1.25，并按引擎折算听感系数
（实测极速引擎同句时长是在线引擎的 **1.41 倍**，因此补偿 1.4，避免「出声更快、念完更慢」）。
语速施加在**播放端**（`playbackRate`，保留音调）而非重新合成——改语速立即生效，也省掉一次合成。

**改后实测（同一轮真实对话）**：

| 指标 | 改前 | 改后 |
|---|---|---|
| 文字出现 → 第一声 | 约 2500ms | **约 890ms** |
| 文字出现 → 首句可播完 | 约 2640ms | **约 1280ms** |
| 首句平均语速 | 约 4.9 字/秒 | 约 6 字/秒（可调至更快） |

界面同时新增「🔊 语音准备中… / 朗读中」状态提示：
1 秒左右的等待被明确说明，而不是看起来像卡住。

### 3.8 语气调制：让情绪被听得见（2026-10-11 追加）

#### 问题

语音上线后暴露一个新问题：**一句话一个音色念到底**。
用户说「我想自残」和说「今天挺开心的」，声音没有任何区别；
文字侧虽然换了危机话术，语气仍然平铺直叙。验收反馈原话是
「感觉若无其事」——在心理陪伴场景里，**语气本身就是回应的一部分**。

#### 方案：同一份情绪配置，同时驱动文字与语音

新增 `src/emotion.py`。每一轮由 `select_emotion()` 判定语气，
输出**两组**参数，二者同源，不会出现「文字紧张、声音平淡」的割裂：

1. **语音侧**：语速 / 音调 / 音量的偏移量，交给 TTS 引擎施加
2. **文字侧**：`prompt_hint` 注入系统提示词，约束该轮模型的情绪浓度

| 语气 | 触发条件 | 语速 | 音调 | 音量 |
|---|---|---|---|---|
| 警觉关切 `alarm` | 危机拦截（当下） | −6% | −3Hz | **+28%** |
| 坚定陪伴 `firm` | 危机后续·加力挽回 | −5% | −2Hz | +22% |
| 认真陪伴 `watch` | 危机后续·持续关注 | −5% | −2Hz | +14% |
| 温柔安抚 `gentle` | 用户情绪很重 / 共情轮 | −8% | −3Hz | +6% |
| 沉稳承接 `steady` | 医疗边界 | −3% | −1Hz | +4% |
| 温和自然 `warm` | 日常默认 | −2% | 0 | +2% |
| 轻快明亮 `bright` | 用户情绪转好 | +5% | +5Hz | +5% |
| 自然 `neutral` | 基准（不做调制） | 0 | 0 | 0 |

**力度阶梯在代码里被断言**（`scripts/test_emotion.py`）：音量必须单调递增
`warm < watch < firm < alarm`，且危机类语气的音调必须比日常更沉。
这样「不能若无其事」不再是一句主观描述，而是一条可回归的约束。

#### 三个设计取舍

1. **危机时变「慢、沉、响」，而不是「快、高、响」**：
   高亢急促会让已经高度紧张的人更慌；慢下来 + 更沉的音色 + 更用力，
   传达的是「我在认真对待这件事」。**情绪浓度靠重量，不靠速度。**
2. **音调偏移限制在 ±12Hz 内**：在线语音音调偏移过大（>10Hz）会明显失真，
   听感变假反而削弱可信度，与「情绪要更真」的目标相反。
3. **语气不能推翻用户偏好**：用户自选语速与情绪语速分别来自长期偏好与本轮表达需要，
   直接相加会出现「用户选了快 + 危机要慢」互相抵消甚至反转。
   因此 `_combine_rate()` 把情绪权重限制在用户语速幅度的一半以内。

#### 语气在界面上可见

- 每条回复下方标签显示 `策略：xxx · 语气：xxx`，让「系统在跟着你调整」这件事被看见
- 气泡样式随语气分级：危机语气加左边框并加强头像色；温柔/轻快语气降低对比度，不制造额外视觉压力

#### 验证

| 项目 | 结果 |
|---|---|
| 情绪识别 | 9/9（含「前几天撑不住，现在好多了」这类正负混合句） |
| 各流程分支语气选择 | 12/12（危机、危机后续、收束、医疗、常规各分支） |
| 语气参数合理性 | 通过（范围 + 力度阶梯单调性断言） |
| 音频差异 | 同一句话 7 种语气生成的 MP3 **指纹各不相同**，体积符合预期（慢的更长、轻快的更短） |
| 端到端对话 | 6 轮实测语气链条：`gentle → alarm → watch → watch → gentle(收束) → warm` |
| 完整评测 | **8/8 场景通过**，策略 8/8，空洞安慰 0%、越界 0%（无回归） |

> **写测试当场抓到两个 bug**：`crisis_closing` 被误判为最高档危机语气（应为温柔的收束语气），
> `medical_referral` 掉进了日常语气（应为平实的沉稳语气）。
> 两者都是分支优先级写反导致的——这类错误在人工点几下界面时很难察觉，
> 但用户会明显感到「语气不对味」。

## 四、评测方法

对应任务目标「让谁去试、试哪些场景、看出什么指标」：

**试什么场景**：**8 个场景、19 轮对话**，覆盖情绪宣泄、表达障碍、决策困惑、安全边界（危机 / 医疗 / 危机后持续关注）、策略轮换五类。

**当前结果**（最近一次运行；因模型采样波动，数值仅供参考）

| 指标 | 当前结果 |
|---|---|
| 边界正确场景数 | 8/8 |
| 策略选择正确场景数 | 8/8 |
| 同策略最长连续轮次 | 1 轮（上限 2） |
| 空洞安慰率 | 0.0% |
| 越界内容率 | 0.0% |
| 平均回复长度 | 66.9 字符 |
| 提问轮次占比 | 86.7% |

评测同时校验三件事：

- **边界是否生效** —— 该拦截的场景是否被拦截
- **策略选择是否符合预期** —— 每个场景定义了 `expect_strategies`，实际策略与之比对
- **策略是否连续重复** —— 部分场景用 `max_consecutive` 约束（如「连续追问导致负担」场景不允许同策略超过 2 轮）

后两项是刻意设计的：若只校验边界，策略选择器可能一直选错策略而无人发现。**开发过程中正是这两项校验暴露了两个真实缺陷**（详见开发日志）：

1. 危机场景轨迹被误清 → 评测误报「未拦截」
2. 用户说「说不上来」时策略失效 → 选了共情，但此时共情无效
3. 连续 7 轮都用探索与澄清 → 提问变成盘问

第 3 项是在**真实试用**（`logs/` 中的对话记录）中发现的，自动化场景未能覆盖。这是「让谁去试」这一环的直接价值。

**谁去试**：已完成作者本人两轮真实试用，记录见 `logs/`。其中第一轮暴露了三个自动化评测未发现的缺陷（连续 7 轮同策略、认知重构成死代码、策略与回复脱节），详见 `logs/试用记录汇总.md` 与开发日志。

**后续需补充**：当前样本仅来自作者本人。仍需邀请 3–5 位同学分别试用，并收集主观评分（被理解程度、有无说教感、是否愿意继续聊）。这部分是自动化指标无法替代的。

### 评测发现并修复的缺陷

开发过程中评测暴露了三个真实问题，均已修复（详见 `docs/开发日志.md`）：

1. **危机场景轨迹被误清** —— `reset()` 同时清空 `trace`，导致评测误报「未拦截」
2. **策略选择器对表达模糊的用户失效** —— 用户说「说不上来」时选了共情，但此时共情无效，应提供描述抓手
3. **连通性脚本误报成功** —— `max_tokens` 过小导致 thinking 阶段耗尽配额，脚本却显示成功

第2 点最关键：它直接对应赛题背景中「学生难以直接描述自身困扰」这一核心特征。

## 六、已知局限

1. **危机识别仍依赖关键词匹配**。词表已从直白表述扩展到委婉表述，并新增**口语插入成分归一化**（把「活着没什么意思」还原成「活着没意思」再比对），回归测试识别率 21/21、普通表达误报 0/10。但关键词方案本质上无法覆盖所有表达方式。例如「反正也没人在乎」这类不触发任何词表的隐晦表述仍可能漏检，真实使用中应叠加语义分类模型。
2. **真实试用样本仍偏少，且记录本身不完整**。`logs/` 中有 6 份同学试用记录（39 轮）+ 2 份作者自测（17 轮），
   但其中 4 份备注含「吴」字、开场句高度相似，**很可能来自同一位同学**，独立试用者可能只有 2–3 位。
   更关键的是：网页版**只有用户主动点「保存记录」才落盘**，因此实际试过的人**远多于留档的 6 位**。
   样本量不足以支撑结论，仍需更多试用者，并收集主观评分。
3. **Web 版会话存在内存中，且无鉴权**。`web.py` 用 Python 字典存储会话，服务重启即丢失，且无法多进程部署。以 `0.0.0.0` 启动时，同网络内任何设备都能访问并消耗 API 额度。若要长期在线或公网使用，需替换为 Redis 等外部存储并加入鉴权。**当前仅建议本机或可信校园网内使用。**
4. **策略执行依赖模型遵守提示词**。已新增 `check_strategy_consistency()` 自动检测偏差，但检测只能发现问题，不能纠正。根治需要结构化输出约束。
5. **`MAX_CONSECUTIVE = 2` 是经验值**，未经临床或文献依据校准。真实使用中可能需要调整为 3，或按不同情绪强度分级。
6. **评测指标存在采样波动**。同一场景多次运行，空洞安慰率等指标会有波动（本项目实测在 0% 与 8.3% 之间变化）。单次评测结果不宜视为定论，严格结论应对同一场景多次运行取均值。
7. **未做年龄验证**。参考 Character.AI 因未成年人保护不足面临多起诉讼的案例，本系统不应部署到面向未成年人的开放环境。
8. **「极速语音」依赖第三方公开接口**。它是本项目的低延迟选项（首音约 0.8 秒），
   但属于非官方接口，**可能被网络屏蔽或随时变更**，且不支持音调/音量调制（情绪只体现在语速上）。
   因此：① 可用性由服务端实测，不可用时自动退回在线语音；② 需要完整情绪表达的场合，建议切回「在线语音」。
   若用于正式产品，应换成有服务协议的商用语音服务（Azure / 讯飞等）。
